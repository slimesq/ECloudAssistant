### 1.1 分清三条路径

用 A 表示控制方客户端，B 表示被控方客户端：

```text
建流协商：A ←→ SigSvr ←→ B
媒体数据：B → RtmpSvr → A
远程输入：A → SigSvr → B → 被控机器的输入系统
```

输入包走信令 TCP 连接，不进入 RTMP 媒体数据。`SigSvr` 负责目标关系和转发；键鼠事件由控制方采集、被控方执行。

后文讨论 `state_` 时，A/B 分别指两端用于这次远控的信令连接。同一个客户端进程可以保有自己的被控连接，同时为控制窗口另建控制连接；角色属于一条 `SigConnection`，不是对整个程序的永久分类。

## 2. 先补 Windows 输入基础

### 2.1 按键事件、键值和字符不是同一件事

| 概念 | 本阶段怎样理解 |
| --- | --- |
| 按下、释放 | 两个独立的状态变化；发送了按下，还需要相应释放 |
| Qt 键值 | `QKeyEvent::key()` 返回的 `Qt::Key`，跨平台逻辑键编号 |
| Windows 虚拟键 | `wVk` 使用的 Windows 键编号，如 A 为 `0x41`、F1 为 `VK_F1` |
| 扫描码 | 标识键盘物理按键的扫描编码；与 Windows 虚拟键和最终输入字符分开理解 |
| 字符文本 | `QKeyEvent::text()` 等提供的文本结果；受布局、修饰键和输入法等影响 |

本项目转发的是按键事件，不是完整的文本输入协议。即使 A 键事件被执行，也不能仅凭键编号保证最终输入的是大写或小写字符。

`MapVirtualKey(vk, 0)` 要求第一个参数是 Windows 虚拟键，第二个参数 0 表示将其映射到扫描码；它不会识别并转换 `Qt::Key`。参见 [QKeyEvent](https://doc.qt.io/qt-6/qkeyevent.html)、[MapVirtualKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-mapvirtualkeya)。

### 2.2 INPUT 与 SendInput 的最小用法

Windows 用 `INPUT` 描述待插入输入流的事件：

| 内容 | 作用 |
| --- | --- |
| `type = INPUT_KEYBOARD` | 使用 `ki` 中的键盘字段 |
| `ki.wVk` | 虚拟键路径中的键编号 |
| `ki.wScan` | 扫描码；设置 `KEYEVENTF_SCANCODE` 后才按扫描码路径解释，届时忽略 `wVk` |
| `ki.dwFlags = 0` | 在本讲的普通虚拟键示例中表示按下 |
| `KEYEVENTF_KEYUP` | 表示释放 |
| `type = INPUT_MOUSE` | 使用 `mi` 中的鼠标字段 |
| `mi.dwFlags` | 表示按钮按下/释放、滚轮或移动等操作 |

先对照官方 [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) 的 `INPUT` 数组写法。下面将其结构简化为普通 A 键的一次按下和释放，是基础学习片段：

```cpp
#include <Windows.h>

UINT sendAKeyPair() noexcept
{
    INPUT inputs[2]{};
    inputs[0].type = INPUT_KEYBOARD;
    inputs[0].ki.wVk = 0x41; // A 键的 Windows 虚拟键
    inputs[1] = inputs[0];
    inputs[1].ki.dwFlags = KEYEVENTF_KEYUP;

    UINT const inserted{SendInput(2, inputs, static_cast<int>(sizeof(INPUT)))};
    return inserted;
}
```

`2` 是事件个数，`sizeof(INPUT)` 是**单个结构**的大小，`inserted` 是成功插入输入流的事件数。它不是目标窗口已处理事件的确认，也不表示向某个指定控件直接发消息。

输入进入执行端的系统输入流，键盘结果与前台窗口、焦点及已有按键状态有关。若已有本地 Qt 测试窗口，可在准备接收普通按键的控件获得焦点后观察；没有现成窗口时，先核对两个结构的字段即可，不要求另建工程。

调用失败时用 `GetLastError()` 辅助判断，不用 Winsock 的 `WSAGetLastError()`。Windows 的 UIPI 也限制向更高完整性级别的应用注入输入；它是“调用了但没有预期结果”时需核对的条件之一。当前项目没有检查 `SendInput` 的返回值。字段说明见 [KEYBDINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput)。

### 2.3 鼠标按钮、移动与滚轮分开理解

- 按钮事件描述本次按下或释放；点击还取决于当前光标位置。
- 移动可以用不同 API 和坐标约定。本项目使用 `QCursor::setPos()`，不是 `MOUSEEVENTF_ABSOLUTE` 的 0～65535 坐标。
- 滚轮传递的是滚动量，Windows 的 `WHEEL_DELTA` 为 120，表示一个标准刻度单位；不能将其直接解释为固定几行。

鼠标字段参见 [MOUSEINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput)。坐标先分清控件内位置、画面内位置和桌面全局位置，具体换算在第 8 节结合项目计算。

## 3. 两种连接与三个识别码用途

### 3.1 本机被控连接在哪里创建

`RemoteWgt` 的本机识别码输入框当前默认填 `"345"`。收到登录成功通知后：

```text
RemoteWgt::handleLogined(ip, port)
  → 读取 selfCodeEdit_ 的本机识别码，空则返回
  → 保存登录返回的信令地址
  → RemoteManager::Init(ip, port, code)
  → 创建并连接 TcpSocket
  → 创建 SigConnection(..., code)      // 默认 CONTROLLED
  → 设置媒体启动、停止回调
```

这条连接将自己的识别码用于 `JOIN`，供控制方查找。当前界面默认值不等于服务端已经分配并持久保存了唯一识别码；这里实际读到的是输入框内容。

### 3.2 控制窗口另建一条信令连接

点击“开始远程”后：

```text
RemoteWgt 读取 rmoteCodeEdit_ 的目标识别码
  → RemoteManager::StartRemote(ip_, port_, targetCode)
  → 创建并显示 PullerWgt
  → PullerWgt::Connect
  → AVPlayer::Connect
  → 创建 SigConnection(..., targetCode, CONTROLLING)
  → 设置媒体启动、停止回调
```

`AVPlayer::Connect()` 返回 true，表示当前连接创建流程走完；它没有等到取流应答或首帧显示。`RemoteManager` 打印的“远程连接成功”也不能作为远控已可用的确认。

区分同一个 `code_` 字段在两种角色中的用途：

| 内容 | 被控连接 | 控制连接 |
| --- | --- | --- |
| 构造传入的 `code_` | 本机识别码 | 要控制的目标识别码 |
| `JOIN` 的 `id` | `code_` | 固定字符串 `"154564"` |
| `OBTAINSTREAM` 的 `id` | 当前角色不主动发送 | `code_`，即目标识别码 |

控制端的固定登记码不是目标码，也不是随机生成的匿名码。多个控制连接使用同一个值，会受到服务端重复登记检查的影响。本阶段理解字段用途即可，不要求多开实验。

## 4. 角色、状态与建流流程

### 4.1 UserType 与 State 分开看

`type_` 是构造时确定的角色；`state_` 随信令处理改变：

| 字段或状态 | 客户端当前含义 |
| --- | --- |
| `CONTROLLED` | 提供本机画面、接收输入的角色 |
| `CONTROLLING` | 请求目标画面、发送输入的角色 |
| `NONE` | 初始状态，尚未处理成功的 JOIN 应答 |
| `IDLE` | JOIN 已成功，处于空闲状态 |
| `PULLER` | 控制连接已进入申请或播放流程，不保证目标存在、拉流成功或已显示画面 |
| `PUSHER` | 被控连接在启动回调返回 true 后设置的本地运行状态，不代表服务端或媒体服务的实时状态 |

客户端与服务端各有各的 `state_`，网络消息不会让两边的变量自动同步。阅读时看清“哪个对象在哪个分支赋值”。

### 4.2 本阶段涉及哪些消息

字段定义都在 `defin.h`，包头与字节流知识不再重学：

| 消息 | 本阶段关注的消息体 | 方向或用途 |
| --- | --- | --- |
| `JOIN` | 请求的 `id`；应答的 `result` | 登记信令连接 |
| `OBTAINSTREAM` | 请求的目标 `id`；应答的 `result` | 控制方请求目标，服务端回复受理结果 |
| `CREATESTREAM` | 通知；回复含 `result / streamAddres` | 通知被控方启动媒体，再回复地址 |
| `PLAYSTREAM` | `result / streamAddres` | 服务端通知控制方播放 |
| `DELETESTREAM` | `streamCount` | 服务端通知关联数量变化 |
| `KEY / MOUSE / MOUSEMOVE / WHEEL` | 键鼠事件字段 | 控制方经信令服务转发给被控方 |

协议中有某种结构，不代表客户端分发器已经处理它。例如 `ObtainStreamReply_body` 已定义，但当前 `HandleMessage()` **没有 `OBTAINSTREAM` 分支**。

### 4.3 正常路径：登记、申请、创建、播放

先假定两条连接能正常登记、被控目标空闲，且媒体启动回调已正确设置：

```text
被控连接 B：
  NONE
    → 发 JOIN(本机码)
    → 收 JOIN 成功
  IDLE，等待目标请求

控制连接 A：
  NONE
    → 发 JOIN(固定登记码)
    → 收 JOIN 成功，先设 IDLE
    → obtainStream() 发 OBTAINSTREAM(目标码)，返回 0
  PULLER

SigSvr 找到 B，通知 B 创建流：
  B 在 IDLE 收 CREATESTREAM
    → 生成 RTMP 地址
    → startStreamCb_(地址)
    → 回调返回 true：回复 CREATESTREAM 成功和地址
  B 设为 PUSHER

SigSvr 将播放地址通知 A：
  A 在 PULLER 收 PLAYSTREAM 成功
    → startStreamCb_(地址)，启动拉流入口
  A 仍为 PULLER
```

这里有三个不同的确认层次：调用 `Send()`、服务端受理请求、媒体实际可用。当前 `obtainStream()` 的返回 0 只说明代码完成了发送调用；阶段四已经说明 `Send()` 还不保证入队成功，更不表示远端已处理。

被控方在 `doCtreatStream()` 中自行拼出 RTMP 地址，源码使用硬编码服务器前缀加递增流编号。它不是信令服务分配的地址，也不由登录返回的信令 IP、port 自动生成。阅读时把它理解为 `rtmp://<媒体服务地址>/live/<流名>`，不要直接照用源码中的局域网地址。

### 4.4 失败路径：目标不存在时为何仍可能是 PULLER

这是最值得和正常路径对照的一次失败：

1. 控制连接收到 JOIN 成功，发出 `OBTAINSTREAM` 后已经将本地状态设为 `PULLER`。
2. 服务端找不到目标，返回失败的 `OBTAINSTREAM` 应答，服务端该连接仍处于 `IDLE`。
3. 客户端没有处理该应答的 switch 分支，走 default 并消费消息，没有回退状态或显示具体失败原因。

结果是：**客户端为 `PULLER`，服务端为 `IDLE`，媒体并未建立。** 不能用本地枚举值推断远端状态。

其他分支只需核对当前动作：

| 情况 | 客户端实际结果 |
| --- | --- |
| JOIN 失败 | 不进入成功分支，保留 `NONE` |
| 被控方启动回调返回 false | 回复 `SERVER_ERROR`，本地仍为 `IDLE` |
| 控制方收到 PLAYSTREAM 失败 | 打印失败，仍为 `PULLER` |
| 控制方启动播放回调返回 false | 当前调用方未检查返回值，状态仍为 `PULLER` |

### 4.5 停止通知没有自动恢复空闲状态

`doDeleteStream()` 读取 `streamCount`，等于 0 时调用 `stopStreamCb_`。它没有把本地 `state_` 恢复为 `IDLE`，也没有根据角色细分不同的停止逻辑。

`streamCount` 是信令关联数量，不是媒体服务器上的流总数。客户端当前未见构造并发送信令 `DELETESTREAM` 的路径；关闭播放器不能解释为已经主动发送了删除请求。

`OnClose()` 也只是设置 `quit_ = true`。本类没有使用这个标志运行退出循环，`eventthread_` 也只是声明，不能把它们讲成已经实现了输入线程停止、媒体清理或自动重连。

## 5. 信令怎样交给媒体模块，在哪个线程执行

### 5.1 只追交接函数

| 信令动作 | 客户端实际交接路径 | 本阶段看清什么 |
| --- | --- | --- |
| 被控方启动 | `doCtreatStream → RemoteManager::HandleStartStream → RtmpPushManager::Open` | 地址传给谁，bool 返回值怎样影响回复和状态 |
| 被控方停止 | `doDeleteStream → RemoteManager::HandleStopStream → RtmpPushManager::Close` | 停止入口怎样被触发 |
| 控制方启动 | `doPlayStream → AVPlayer::HandleStartStream → avDEMuxer_->Open`，再创建音视频播放线程 | 播放地址的消费方与线程启动位置 |
| 控制方停止 | `doDeleteStream → AVPlayer::HandleStopStream → Close` | 通知如何进入播放器关闭入口 |

当前 [AVDEMuxer::Open()](../Codec/AVDEMuxer.cpp) 只创建执行 `FetchStream()` 的读线程，随后立即返回 true；实际打开媒体和读取流信息在该工作线程中进行。`AVPlayer::HandleStartStream()` 不等待这个异步结果，就继续创建音视频播放线程并返回 true，`doPlayStream()` 也没有检查它的返回值。因此回调被调用、媒体打开成功、首帧出现，是不同的观察点。

### 5.2 回调绑定在构造返回之后

实际顺序是：

```text
TcpConnection 基类构造：注册 Channel
  → SigConnection 构造：设置读/关闭回调，立即 Join()
  → 构造返回
  → RemoteManager / AVPlayer 设置媒体启动、停止回调
```

调度线程此时已经运行，回调设置与收包处理之间存在时序窗口。默认启动回调返回 true、默认停止回调不执行操作；两者都是可调用的函数，不能将默认返回值当成媒体确已启动。

### 5.3 普通 C++ 回调不会自动切换到 GUI 线程

| 行为 | 当前执行线程 |
| --- | --- |
| 点击按钮、创建控制窗口、Qt 键鼠事件处理 | GUI 线程 |
| `OnRead → HandleMessage → doJoin / doCtreatStream / doPlayStream` | 信令连接所属调度线程 |
| 从上述信令处理直接调用媒体启动/停止回调 | 仍是当前调度线程 |
| Qt 输入处理函数调用 `Send` 时的首次发送尝试 | GUI 调用线程，复用阶段四结论 |

即使回调调用的是 `RemoteManager / AVPlayer` 的成员函数，直接调用仍在当前信令调度线程中执行，不会自动变成 Qt queued 调用。若调用链涉及 GUI 对象或阻塞式媒体启动，需要核对实际线程和 API 要求。完整的初始化、跨线程停止和对象销毁顺序留阶段九。

## 6. 信令分发前，消息必须完整且解析必须推进

`SigConnection::OnRead()` 在 `ReadableBytes() > 0` 时反复调用 `HandleMessage()`。后者先把 `Peek()` 转为包头指针，读取 `head->len`，再判断完整消息是否到齐。

与阶段三的解析顺序对照，当前有三个直接影响：

1. **包头还没到齐就读取长度。** 可读字节应先满足包头大小；底层 vector 有空间，不代表收到的字节已经构成有效包头。
2. **半包返回后外层没有停。** 假设缓冲里有 5 字节，头部声明整条消息需要 7 字节，内层返回且不消费，外层仍因缓冲非空继续调用，可能一直占用调度线程。
3. **长度与命令的消息体没有充分校验。** 还需要长度下限和具体消息体大小检查。长度为 0 时也不能保证消费推进；仅有一个包头不能直接按键鼠消息体访问字段。

正确的阅读判断顺序仍是：包头足够 → 长度合法 → 完整消息足够 → 按命令核对字段 → 处理并消费；数据不足时结束本轮解析，等待下一次收包。

本阶段能定位这些条件及其后果即可，不要求重写解析器。输入执行建立在消息已经完整且字段有效的前提上。

## 7. 键盘：从 Qt 事件到 Windows 输入

### 7.1 正常想表达的字段与实际路径

```text
AVPlayer::keyPressEvent / keyReleaseEvent
  → Key_Body(type, key)
  → TcpConnection::Send
  → SigSvr 根据控制连接的目标关系转发
  → 被控 SigConnection::HandleMessage(KEY)
  → doKeyEvent
  → INPUT_KEYBOARD → SendInput
```

`Key_Body` 中 `type` 的约定为 `PRESS = 0、RELEASE = 1`；接收端用 `body->type ? KEYEVENTF_KEYUP : 0` 选择释放或按下。

输入包自身没有目标识别码，服务端靠事先保存的控制关系转发，并检查服务端该连接的状态和目标关系。若已取得地址但输入不转发，还需对照 ENET 阶段七的 `conn_` 关系；服务端复用已有推流地址的分支存在遗漏目标连接赋值的问题。

当前 Qt 输入函数只检查 `!sig_conn_->IsClosed()`，没有先判连接指针是否为空，也没有核对 `PULLER`、画面矩形或首帧是否可用。因此“连接未关闭”不是输入准备完成的充分条件。

Qt 键盘事件由有键盘焦点的控件接收，这里不是全局键盘 Hook。`AVPlayer` 构造中调用了 `setFocus()`；实际没有进入事件函数时，先检查当前焦点与事件接收对象。

### 7.2 当前释放事件漏写了 type

`keyPressEvent()` 设置 `body.type = PRESS`，然后写入键值；但 `keyReleaseEvent()` 实际写的是：

```cpp
body.key = MouseKeyType::RELEASE;
body.key = event->key();
```

第一句写错了字段，又被第二句覆盖，`body.type` 始终没有赋值。`Key_Body` 构造也不初始化它，所以不能将接收端看到的值解释为可靠的释放标志。

例如，想表达 A 键按下/释放，应分别得到 `(PRESS, 0x41)` 与 `(RELEASE, 0x41)`；当前按下分支能写出前一组，释放分支不能保证后一组。识别这个字段错误即可，不依赖实际制造“按键卡住”的现象。

### 7.3 Qt 键值不能直接当 Windows 虚拟键

发送端将 `event->key()` 的 int 值放入 `uint16_t key`，被控端再直接赋给 `wVk`：

| 按键 | Qt 键值 | 当前写入 uint16_t 后 | Windows 需要的虚拟键 |
| --- | --- | --- | --- |
| A | `0x41` | `0x41` | `0x41`，这一项恰好相同 |
| F1 | `0x01000030` | `0x0030` | `VK_F1 = 0x70` |

`0x30` 在 Windows 表示数字 0 键，不是 F1。一个普通字母可用，不代表整套键值已正确映射。对照 [Qt::Key](https://doc.qt.io/qt-6/qt.html#Key-enum) 与 [Windows Virtual-Key Codes](https://learn.microsoft.com/en-us/windows/win32/inputdev/virtual-key-codes)。

接收端虽然填了 `wScan = MapVirtualKey(vk, 0)`，但没有设置 `KEYEVENTF_SCANCODE`，当前仍按虚拟键路径解释；这一步也无法修复此前的 Qt 键值截断。完整修饰键、扩展键与布局处理不要求在本阶段实现，先把字段约定和已有缺口说明白。

## 8. 鼠标：按钮、坐标与滚轮各走什么路径

### 8.1 按钮包只描述本次变化，不携带坐标

`mousePressEvent / mouseReleaseEvent` 分别写 `PRESS / RELEASE`，用 `event->button()` 写入本次变化的按钮。它不同于 `buttons()` 所表达的全部按住按钮集合，参见 [QMouseEvent](https://doc.qt.io/qt-6/qmouseevent.html)。

`doMouseEvent()` 按左、右、中键生成相应 `MOUSEEVENTF_*DOWN / *UP`，调用 `SendInput`。协议虽然也声明了 XButton1、XButton2，接收代码当前只处理前三种。

`Mouse_Body` 没有位置字段，接收端这个分支也不移动光标。点击位置依赖独立的 `MOUSEMOVE` 消息此前把被控端光标移到了哪里。

### 8.2 GetPosRation 先找到画面内的位置

`OpenGLRender` 启用 `setMouseTracking(true)`，因此不按住按钮时也可收到移动事件。`AVPlayer::mouseMoveEvent()` 调用 `GetPosRation()` 填写坐标比例。

该函数实际取 `QCursor::pos()`，而非直接使用本次 `QMouseEvent` 的坐标：

```text
当前全局光标位置
  → mapFromGlobal：控件内位置
  → 减 m_rect.topLeft()：实际画面内位置
  → 除 m_rect.width / height：相对画面的比例
```

`m_rect` 来自 `resizeGL()` 的等比缩放与居中计算。播放器和远端画面比例不同时会留边，不能直接拿整个播放器宽高归一化。本阶段只读这段几何计算，不展开 OpenGL 绘制。

### 8.3 四个字节怎样保存比例

以 x 方向为例，先将比例转成百分数 `p`：

```text
p        = 画面内 x / 画面宽度 * 100
xl_ratio = p 的整数部分
xr_ratio = (p - xl_ratio) * 100 的整数部分

接收比例 rx = (xl_ratio + xr_ratio / 100.0) / 100.0
```

y 方向同理，使用 `yl_ratio / yr_ratio`。这是百分数的整数部分加两位小数部分，不是直接传一个 double，也不是传屏幕像素坐标。

例如百分数 25.5 编成 `(xl_ratio, xr_ratio) = (25, 50)`，再按 `(25 + 50/100.0)/100.0` 恢复为比例 0.255。有效范围内的浮点转整数采用截断，不是四舍五入。

被控端 `doMouseMoveEvent()` 按当前代码恢复：

```text
x = int(rx * screen_->size().width()  / screen_->devicePixelRatio())
y = int(ry * screen_->size().height() / screen_->devicePixelRatio())
QCursor::setPos(x, y)
```

这里 `screen_` 保存的是主屏。`QCursor::setPos(x, y)` 使用桌面全局坐标，见 [QCursor](https://doc.qt.io/qt-6/qcursor.html#setPos)。

### 8.4 用一个带留边的例子手算

假定当前数值如下：

| 项目 | 数值 |
| --- | --- |
| 播放器尺寸 | 800 × 600 |
| 16:9 画面的显示矩形 | `m_rect = (0, 75, 800, 450)` |
| 光标在控件内的位置 | `(200, 165)` |
| 被控端主屏 size、DPR | 1920 × 1080、1 |

计算得到：

```text
画面内位置 = (200 - 0, 165 - 75) = (200, 90)
比例       = (200/800, 90/450)   = (0.25, 0.20)
发送字段   = xl/xr/yl/yr         = 25/0/20/0
恢复位置   = (0.25*1920, 0.20*1080) = (480, 216)
```

如果误用整个播放器高度，y 比例会算成 `165/600 = 0.275`，远端 y 会变成 297，而不是 216。这就是必须扣除留边、使用画面尺寸的原因。

当前实现没有先检查画面矩形宽高是否大于 0，也没有处理落在留边外的点。不能依靠转换为 `uint8_t` 来限制范围。

### 8.5 DPI 与多屏只先核对坐标单位

上例用 DPR = 1，是为了先看清几何与协议。Qt 高 DPI 模型中的控件、事件和屏幕几何通常使用逻辑坐标，图像像素则可能是物理像素，参见 [Qt High DPI](https://doc.qt.io/qt-6/highdpi.html)。

因此不能把源码中的“除以 DPR”讲成通用正确做法：如果 `screen_->size()` 已经是逻辑尺寸，再除一次会缩小位置。当前代码还固定使用主屏，未加上屏幕几何原点，也没有选择其他屏幕。

本阶段能区分单位、指出当前假设即可。实际出现缩放或多屏偏移时，再对照画面来源和目标屏幕深入。

### 8.6 滚轮只保留方向，再变成固定增量

`pixelDelta()` 表示以屏幕像素为单位的滚动距离，`angleDelta()` 以 1/8 度为单位；常见鼠标的一档为 15 度，对应后者的 120。这两个 delta 的原始单位不同。

`wheelEvent()` 优先看非空的 `pixelDelta()`，否则看 `angleDelta()`，只根据 y 的正负写 `int8_t wheel = ±1`。原始增量幅度没有保留，零 y 值也会被当前三元表达式归为 -1。

被控端按 `body->wheel * 240` 填 `mouseData`，设置 `MOUSEEVENTF_WHEEL` 后调用 `SendInput`。所以一个发送事件被恢复为正或负的两个标准刻度单位，**不是两行**；最终滚动多少由目标应用和系统设置决定。Qt 的两种 delta 及其单位见 [QWheelEvent](https://doc.qt.io/qt-6/qwheelevent.html)。

## 9. 用状态推演和一次输入字段观察核对

建议按以下步骤学习，不依赖完整远控先成功：

1. 先读第 2 节，认识普通 A 键按下/释放的两个 `INPUT`。有现成 Qt 测试窗口时按需观察；条件不足时完成字段推演即可。
2. 沿两条连接入口区分三个识别码用途，再对照第 4 节追正常建流和目标不存在的状态变化。
3. 在键盘与鼠标中选一条事件路径，核对 Qt 字段、协议字段和执行 API；坐标部分用第 8.4 节算例确认留边和比例含义。

已有可用信令连接与调试条件时，可在 `AVPlayer` 对应事件函数填完消息体后设断点，查看 `type / key` 或鼠标字段；已有双端条件时再跟到 `doKeyEvent / doMouseEvent / doMouseMoveEvent / doWheelEvent`，核对实际线程和输入结果。不要求为此新搭服务。

完整双端画面、声音和输入验收继续复用 ENET [阶段十二](https://github.com/slimesq/ENET/blob/main/docs/项目学习规划.md#stage-12)。本阶段定位到具体状态、字段或调用即可，不要求修完全部状态、输入和退出问题。
