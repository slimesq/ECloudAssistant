# ECloudAssistant 阶段一：已有基础复用与源码阅读方法学习讲义

> 对应[项目学习规划的阶段一](项目学习规划.md#stage-1)。按需查阅，不设统一课时。
>
> 已有 C++、Linux socket/epoll 和 ENET 源码阅读经验直接复用。本讲围绕客户端的一个回调，说明怎样查清调用、对象和线程关系；当前没有疑问时，直接进入[阶段二](项目学习规划.md#stage-2)。

## 1. 先明确当前要解释什么

遇到不理解的代码时，先把问题落到一个具体行为上。例如：

- `SetStartStreamCallBack()` 立即启动推流，还是只保存回调？
- 回调捕获的 `this` 指向哪个对象，该对象由谁持有？
- 这个成员函数在 GUI 线程还是网络线程执行？
- 一个停止标志由谁写、谁读，双方怎样同步？

用编辑器的“转到定义”和“查找引用”寻找答案。熟悉的语法直接使用；只补当前说不清的概念，再回到原来的函数。已掌握 ENET 阶段一的方法时，可以直接看下面的客户端案例。

## 2. 案例：追踪启动流回调

本例只回答“回调在哪里保存、何时调用、捕获哪个对象”，读到 `RtmpPushManager::Open()` 的调用入口即可。信令状态机在阶段五学习，采集、发布和播放在阶段六至八学习。

相关位置：

| 文件 | 当前要找的内容 |
| --- | --- |
| [RemoteManager.cpp](../UI/center/RemoteManager.cpp) | 注册回调、处理传入的流地址并调用 `Open()` |
| [SigConnection.h](../Net/SigConnection.h) | 回调类型、保存回调的成员和 setter |
| [SigConnection.cpp](../Net/SigConnection.cpp) | 处理消息时调用回调的分支 |
| [RemoteWgt.h](../UI/center/RemoteWgt.h)、[RemoteManager.h](../UI/center/RemoteManager.h) | 需要确认谁持有对象时再查成员声明 |

### 2.1 注册时保存了什么

`RemoteManager::Init()` 连接信令服务成功、创建 `sig_conn_` 后，执行以下源码：

```cpp
sig_conn_->SetStartStreamCallBack(
    [this](QString const& streamAddr) { return this->HandleStartStream(streamAddr); });
```

再看 `SigConnection.h` 中的定义：

```cpp
using StartStreamCallBack = std::function<bool(QString const& streamAddr)>;
inline void SetStartStreamCallBack(StartStreamCallBack const& cb)
{
    startStreamCb_ = cb;
}
```

这里把可调用对象复制到成员 `startStreamCb_`。虽然参数 `cb` 是引用，成员保存的不是该参数引用；setter 返回后，回调仍在。

注册时不执行 lambda 的函数体。`[this]` 保存的是当前 `RemoteManager` 的对象指针，留待以后调用 `HandleStartStream()`，没有复制整个对象，也不会延长其寿命。

### 2.2 找到调用点，再查参数与返回值

查找 `startStreamCb_` 的使用位置。本例选择被控端的 `SigConnection::doCtreatStream()` 路径；函数名沿用源码中的拼写。

以下以 `Init()` 已完成本例的回调注册为前提。`HandleMessage()` 将 `CREATESTREAM` 消息分发给 `doCtreatStream()`。后者检查 `state_ == IDLE`、`type_ == CONTROLLED`，即当前是否为空闲的被控端；满足条件后构造流地址 `streamAddr`，再在回调非空时调用 `startStreamCb_(streamAddr)`。路径可缩为：

```text
SigConnection::HandleMessage
  → doCtreatStream
  → startStreamCb_(streamAddr)
  → 注册时保存的 lambda
  → RemoteManager::HandleStartStream(streamAddr)
  → RtmpPushManager::Open(streamAddr)
```

沿这条路径分别看两件事：

- **参数**：流地址由 `doCtreatStream()` 生成，作为参数逐层传入；它不是注册回调时就固定下来的值。
- **返回值**：`HandleStartStream()` 返回 `Open()` 的结果，调用方再据此填写响应、更新状态。

当前代码将回调返回 `true` 作为发送成功响应并转为 `PUSHER` 的条件，但这不能直接证明 RTMP 服务端已经确认发布成功。返回值代表哪一步完成，要继续查实现；具体语义在[阶段五](项目学习规划.md#stage-5)与[阶段七](项目学习规划.md#stage-7)核对。

还要注意成员的初始值：`startStreamCb_` 默认就是一个返回 `true` 的 lambda。因此，`if (startStreamCb_)` 只检查是否保存了可调用对象，不能证明它已经被替换成本例中调用 `RemoteManager` 的回调。

### 2.3 确认对象由谁持有

把成员声明与创建位置一起看，而不是仅凭 `new` 或指针类型下结论：

| 当前代码 | 能确定的持有关系 |
| --- | --- |
| `RemoteWgt::manager_` 是 `unique_ptr<RemoteManager>` | 窗口构造时创建管理对象，智能指针负责在释放时销毁它 |
| `RemoteManager::event_loop_` 是 `unique_ptr<EventLoop>` | 管理对象持有这一组网络调度资源 |
| `RemoteManager::sig_conn_` 是 `shared_ptr<SigConnection>` | 该成员持有信令连接，连接寿命还要看其他持有者 |
| `SigConnection::startStreamCb_` 中的 `[this]` | 保存 `RemoteManager*`，没有形成对管理对象的共享持有 |

因此，`SigConnection` 仍然存活，不代表回调中 `this` 指向的 `RemoteManager` 也仍然存活。要判断关闭时是否安全，还需核对回调是否可能继续执行、线程是否已经结束；完整关闭关系放到[阶段九](项目学习规划.md#stage-9)。

客户端还有 Qt parent 这种持有方式。例如 [RemoteWgt.cpp](../UI/center/RemoteWgt.cpp) 中的 `new QLineEdit(this)`、`new QPushButton(..., this)` 将控件交给父对象管理，父对象析构时会删除仍归它所有的子对象。成员虽然是裸指针，也不能据此认定需要逐个手动删除，见 [Qt 对象树与所有权](https://doc.qt.io/qt-6/objecttrees.html)。

`RemoteManager` 间接继承 `QObject`，但这里没有给它设置 QObject parent，而是由 `manager_` 管理。对象的 C++ 持有方式、Qt parent 和回调捕获是三个需要分别确认的关系。

## 3. 线程或并发有疑问时怎样补

### 3.1 从调用点判断实际执行线程

`std::function` 和 lambda 本身不会切换线程。本例的启动流回调是普通 C++ 调用，不是 Qt signal/slot。

若要继续确认线程，向调用方追到 [TcpConnection::HandleRead()](../Net/TcpConnection.cpp)、[SelectTaskScheduler::HandleEvent()](../Net/SelectTaskScheduler.cpp)，再看 [EventLoop::Loop()](../Net/EventLoop.cpp) 如何创建工作线程。沿正常读事件路径，回调在分发该连接事件的网络调度线程中同步执行。

“对象在哪个线程创建”和“当前函数在哪个线程执行”需要分开判断。`RemoteManager` 虽在界面构造过程中创建、间接继承 `QObject`，普通成员函数调用也不会自动回到 GUI 线程。

客户端同时存在几种调用方式。下面的 `context` 是 Qt 连接时传入的 `QObject`；Qt 用它确定排队调用交给哪个线程，并关联连接的生命周期。

| 看到的写法 | 怎样判断线程 |
| --- | --- |
| `callback(args)`、普通成员函数调用 | 继续在调用者线程执行，除非内部明确另行调度 |
| `QObject::connect(..., context, lambda)` | 查连接类型、信号实际发出线程及 context 的线程归属 |
| `Qt::QueuedConnection`，如 [AVPlayer.cpp](../Puller/UI/AVPlayer.cpp) 的 `sig_repaint` | 将调用排队，交给接收对象所属线程的 Qt 事件循环处理 |

对于 Qt 默认的 `AutoConnection`，信号实际发出线程与接收对象所属线程相同时直接调用，否则排队调用。GUI 控件操作应在主线程进行。相关规则见 [Threads and QObjects](https://doc.qt.io/qt-6/threads-qobject.html)，在[阶段二](项目学习规划.md#stage-2)结合项目补学。

Qt 连接与普通回调的生命周期规则也不同。`RemoteWgt` 的按钮连接将第三个参数 `this` 作为 context；发送者或 context 销毁时，Qt 会自动断开该连接。但本例保存在 `std::function` 中的回调没有这套自动断连规则，见 [QObject::connect](https://doc.qt.io/qt-6/qobject.html)。Qt 自动断连也不代替工作线程的停止与等待。

### 3.2 查共享状态，先找读写双方

对象是否存活、成员的并发访问是否安全，需要分别判断。`shared_ptr` 可以保持对象存活，但不会自动保护对象中的业务数据。

遇到共享字段时，查清：谁读、谁写、双方在哪个线程、这些访问通过什么方式协调。例如：

| 位置 | 从声明和使用处能确定什么 |
| --- | --- |
| [TaskScheduler.h](../Net/TaskScheduler.h)、[TaskScheduler.cpp](../Net/TaskScheduler.cpp) 的 `is_shutdown_` | 是 `atomic_bool`；工作线程在 `Start()` 中读取，`Stop()` 写入停止请求 |
| [RtmpPushManager.h](../Pusher/RtmpPushManager.h)、[RtmpPushManager.cpp](../Pusher/RtmpPushManager.cpp) 的 `exit_`、`isConnect` | 是普通 `bool`；`Close()` 写入，已启动的编码线程在循环中读取，这些访问没有相应的同步保护 |

跨线程访问同一数据时，若至少一方写入、至少一次访问不是原子操作，且冲突访问之间没有建立必要的同步顺序，就会形成 data race，导致未定义行为，不能仅理解成“偶尔读到旧值”，见 [C++ data races 规则](https://eel.is/c++draft/intro.races)。

阅读加锁代码时，还要查实际加锁范围，以及读写双方是否使用同一把锁。声明里有 `mutex`、某一个字段用了原子类型，都不能单独证明整个对象线程安全。这里先识别当前缺口，完整停止流程与资源关系在阶段九集中核对。

### 3.3 区分停止请求和 join

[EventLoop::Quit()](../Net/EventLoop.cpp) 先对调度器调用 `Stop()`，再调用 `join()`。这段代码希望实现的停止过程是：

```text
Quit 调用线程：Stop() 发出请求 → join() 等待线程结束 → 后续清理
工作线程：检查停止标志 → 退出循环 → 线程结束
```

`join()` 是等待线程结束，不会代替停止请求；`joinable()` 也不表示线程仍在运行。若线程对象放在智能指针中，还要先区分“指针是否为空”与“线程是否可 join”，见 [C++ thread 成员规则](https://eel.is/c++draft/thread.thread.member)。

设计意图还要与实际时序核对：`Start()` 会把停止标志重置为 `false`，若停止请求早于工作线程进入 `Start()`，请求可能被覆盖。完整启动与退出顺序、阻塞调用、回调和资源释放在阶段九展开。

## 4. 按当前疑问选择核对办法

源码可以确定赋值、保存和条件调用关系；某次运行是否走到该分支、当时的参数值及线程 ID，则需要实际观察。

| 当前疑问 | 下一步 |
| --- | --- |
| 某个语法或 API 的含义不清楚 | 查声明、对应版本文档，必要时用一个短片段确认 |
| 知道 API，但不清楚本项目为何调用它 | 查调用方、成员赋值和使用位置 |
| 不知道实际走了哪个分支、传入什么值 | 查看已有日志，或在相关函数设断点看参数和调用栈 |
| 不知道回调在哪个线程执行 | 在回调断点处查看线程，与注册位置比较 |
| 缺少当前主题的理论基础 | 回到该主题所在阶段，先补概念与现成示例，再读实现 |
| 环境阻断运行 | 按[阶段零讲义](阶段00_工程与构建基线学习讲义.md)定位问题，先推进不依赖运行的源码阅读 |
| 实现与预期不一致 | 查条件、返回值和资源状态；已理解的小问题可最小修复，其余保留未解点 |

本例无需先运行完整远控或推流。运行条件齐全时，可以在注册回调处与 `HandleStartStream()` 观察两个时刻；条件不足时，先完成源码推演，明确哪些结果尚未实测即可。

Qt 对象与调用基础在[阶段二](项目学习规划.md#stage-2)，Windows 网络与调度在[阶段四](项目学习规划.md#stage-4)，采集编码在[阶段六](项目学习规划.md#stage-6)，播放与渲染在[阶段八](项目学习规划.md#stage-8)。这些主题的基础学习仍按对应阶段安排。
