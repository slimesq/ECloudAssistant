## 2. 先补读源码所需的音视频基础

已有把握的部分直接对应项目字段；不熟悉的部分按本节顺序补。依赖定位沿用阶段零，仓库没有锁定 FFmpeg 版本，示例与实际使用的头文件、库和 DLL 要相容。

### 2.1 原始图像、像素格式与 linesize

| 格式或字段 | 含义 |
| --- | --- |
| BGRA | 每像素 B、G、R、A 四个字节 |
| BGR0 | 同样占四字节，但第四字节不是有效 alpha |
| YUV420P | 8 位 Y、U、V 三个平面；U/V 在两个方向各缩小一半 |
| `data[i]` | 相应平面的数据起点 |
| `linesize[i]` | 走到该平面下一行的字节步长，可能含 padding，也可能为负 |
| width/height | 图像尺寸，不等于每行实际占用的存储字节数 |

对偶数宽高、无 padding 的图像，BGRA 占 `W×H×4` 字节，YUV420P 占 `W×H×3/2` 字节。这个公式只算紧凑存储量，不能代替实际 Frame 的 `linesize`。

例如 BGRA 宽 3、高 2，每行有效数据 12 字节，但源 `linesize=16`：第二行从源地址 +16 开始。直接拷前 24 字节会把第一行的 padding 当成第二行的一部分。应依据行跨度复制；打包到紧凑缓冲后，才得到连续的 24 字节。

本项目已经使用图像辅助 API 处理采集端的行跨度，见第 4 节。接口说明参见 [AVFrame](https://ffmpeg.org/doxygen/8.0/structAVFrame.html)、[图像尺寸与复制 API](https://ffmpeg.org/doxygen/8.0/group__lavu__picture.html)。

### 2.2 PCM：每声道样本数、排列与字节数

PCM 是尚未压缩的音频样本。先分清：

| 名称 | 含义 |
| --- | --- |
| sample rate | 每声道每秒的样本数，如 48000Hz |
| channels | 声道数；完整声道布局还包含各声道的含义 |
| S16 | 每样本为 16 位有符号整数，packed/interleaved 排列 |
| FLT | 每样本为 float，packed 排列 |
| FLTP | 每样本为 float，planar 排列，每声道各有一块数据 |
| `nb_samples` | 一个音频 Frame 中**每声道**的样本数，不是全部声道样本总和 |

双声道 packed 数据按 `L0,R0,L1,R1,...` 交错；planar 数据则分别保存 `L0,L1,...` 和 `R0,R1,...`。S16 到 FLTP 既改变数值表示，也改变排列，`memcpy` 不会完成这种转换。

WASAPI 的一个 audio frame 是同一时刻各声道样本组成的一组。本项目回调和 `Read(samples)` 中的 samples 也按这个数量理解：

```text
字节数 = 每声道样本数 × 声道数 × 每样本字节数
S16、双声道、1024 sample frames = 1024 × 2 × 2 = 4096 字节
48000Hz 下的时长 = 1024 / 48000 秒 ≈ 21.33ms
```

这里的 audio frame、FFmpeg 的 `AVFrame` 容器和视频的一张图像，不是同一个计数单位。采样格式参见 [FFmpeg Audio sample formats](https://ffmpeg.org/doxygen/8.0/group__lavu__sampfmts.html)。

### 2.3 Frame、Packet 与编码输入输出

在本阶段的编码方向上：

```text
视频：原始图像 AVFrame → 编码器 → H.264 AVPacket
音频：原始 PCM AVFrame → 编码器 → AAC AVPacket
```

`AVFrame` 描述原始数据及格式、尺寸/样本数等；`AVPacket` 保存编码数据及时间戳等信息。一个 Packet 不是 TCP 包。

NAL 是 H.264 码流的组成单元，可以承载图像切片或 SPS/PPS 等参数。一张图像可以涉及多个 NAL，一个 Packet 也可以包含多个 NAL，不能将它们按数量一一对应。概念说明见 [NAL 单元概述](https://datatracker.ietf.org/doc/html/rfc6184#section-1.3)。

`av_frame_alloc / av_packet_alloc` 首先分配结构；视频或音频 Frame 还要设置字段，再用 `av_frame_get_buffer` 分配数据缓冲。结构的寿命与其引用的数据寿命需要分别理解，具体持有关系在第 8 节核对。

### 2.4 send/receive 不是“一进一出”

先对照官方 [encode_video.c](https://ffmpeg.org/doxygen/8.0/encode_video_8c-example.html) 的编码函数，再看 [encode_audio.c](https://ffmpeg.org/doxygen/8.0/encode_audio_8c-example.html) 怎样填写音频字段。音频示例编码的是 MP2，不能把其格式、frame_size 等参数直接当作本项目 AAC 的参数。

需要读懂的调用顺序：

```text
准备并填写 Frame
  → avcodec_send_frame
  → 循环 avcodec_receive_packet
      成功：消费 Packet，再取下一个输出
      EAGAIN：当前暂无更多输出，继续提供输入
      EOF：编码器已结束输出
      其他错误：按返回码处理

正常结束：
  → avcodec_send_frame(ctx, nullptr)，传空指针进入 drain
  → 继续接收并消费输出，直到 EOF
```

一次输入可以暂时没有输出，也可能产生多个输出。send 若返回 EAGAIN，应先取走输出，再重试尚未被接受的输入；单纯等待时间不会推动编码器状态。正常收尾的 drain 用于取尽内部缓冲数据，不能用释放上下文替代。

项目的音视频编码当前都只 send 一次、receive 一次，将 EAGAIN/EOF 等归为无 Packet，并没有完整的输出循环与结束 drain。因此 `Encode()` 返回空指针不宜直接解释成“这张图或这块 PCM 编码失败”。参见 [FFmpeg send/receive 模型](https://ffmpeg.org/doxygen/8.0/group__lavc__encdec.html)。

### 2.5 时间戳必须带着时间基解释

`time_base = {num, den}` 表示一个计数单位对应多少秒：

```text
时间（秒）= 时间戳 × num / den
PTS=3，time_base=1/30        → 0.1 秒
PTS=4800，time_base=1/48000  → 0.1 秒
```

PTS 表示呈现时间，DTS 表示解码时间；有帧重排时两者可能不同。编码器配置的时间基不会自动使调用循环以该帧率运行，也不会自动替上层填写正确的 PTS。

`av_rescale_q` 用于在时间基之间换算计数。编码器输出与后续封装使用的时间基也要区分，本项目另用运行时长生成发布毫秒时间戳，见第 7 节。

## 3. 先认清采集和编码分别何时启动

### 3.1 Init 已经启动采集

沿阶段五的推流启动回调进入：

```text
RemoteManager::HandleStartStream
  → RtmpPushManager::Open
      → Init
          创建 Publisher
          初始化屏幕采集并启动采集 QThread
          打开 H.264 编码器
          初始化音频采集并启动 WASAPI 采集线程
          打开 AAC 编码器
          复制编码配置，SetMediaInfo
      → Publisher::OpenUrl
          建立 TCP，发起 RTMP 握手
      → 创建 EncodeVideo / EncodeAudio 工作线程
```

`OpenUrl()` 返回并不表示 RTMP 发布命令已完成，`isConnect = true` 也不是媒体服务已确认发布的状态；相关协议留阶段七。采集比编码工作线程更早启动，不能把 `Init()` 理解为只填写参数。

### 3.2 采集与编码分别在哪个线程执行

| 路径 | 当前执行位置 |
| --- | --- |
| `Open / Init` 的主要编排 | 主信令调用路径中是信令调度线程，复用阶段五结论 |
| 屏幕 `GetOneFrame / Decode` | `GDIScreenCapture` 自己的 QThread |
| WASAPI `capture` 与同步 PCM 回调 | `WASAPICapture::start()` 创建的 std::thread |
| `EncodeVideo` | 管理器的 `videoCaptureThread_`，实际做视频取帧、编码和提交 |
| `EncodeAudio` | 管理器的 `audioCaptureThread_`，实际做音频读缓冲、编码和提交 |

后两者名字含 Capture，但不等于底层采集线程。编码库还可能有自己的线程，这张表不用于计算整个进程的线程总数。

## 4. 视频：桌面图像怎样成为 H.264

### 4.1 gdigrab 的实际配置和输出

`GDIScreenCapture::Init()` 以 `gdigrab` 打开 `"desktop"`，当前设置：

| 参数 | 当前值或行为 |
| --- | --- |
| 采集区域 | 固定 `2560×1440`，偏移 `(0,0)` |
| 采集帧率 | 配置值 25 |
| 鼠标 | `draw_mouse=1` |
| `display_index` | 参数未参与屏幕选择 |
| 取得图像 | `av_read_frame → send_packet → receive_frame` |

设备输入由 FFmpeg 的输入接口提供，因此仍会看到 Packet 和解码步骤；不能把这里的解码器理解成正在解码远端 H.264。

初始化时曾设置 `codec_context_->pix_fmt = RGBA`，其后又复制输入流参数。这不构成像素转换，最终应看收到的 `AVFrame::format`。当前 `Decode()` 只接受 **BGRA/BGR0**；两者颜色通道布局相同，本路径转换到 YUV 时不依赖第四字节的 alpha 含义。设备参数见 [gdigrab](https://ffmpeg.org/ffmpeg-devices.html#gdigrab)。

### 4.2 先打包为独立内存，再复制给编码线程

当前数据交接是：

```text
采集线程：
  解码 AVFrame
    → 检查 format、width、height
    → av_image_get_buffer_size(..., align=1)
    → av_image_copy_to_buffer(data, linesize, ...)
    → 加锁替换“最新图像”
    → av_frame_unref

编码线程：
  CaptureFrame 加锁
    → 将最新图像复制到调用方 vector
    → 返回实际 width/height
```

采集端已经依据源行跨度移除 padding，并处理负 linesize；这不是直接盲拷 `width×height×4`。复制后的图像不依赖解码 Frame 继续存活，编码线程的 vector 又是另一份数据。

这里保存的是**最新一张图像**，不是逐帧队列。编码取帧快时可能重复取得同一画面，慢时可能跳过中间图像；代码没有把每张采集图像及其采集时刻逐项排队。

### 4.3 BGRA 到 YUV420P：转换器与输入拷贝分别看

`VideoEncoder` 用 `VideoConverter::Open` 创建 `SwsContext`，指定输入尺寸/格式和编码目标尺寸/格式，随后由 `sws_scale` 做缩放与格式转换。输出 Frame 每次分配，目标为 YUV420P。

但送入转换器之前，当前 `VideoEncoder::Encode()` 将字节用整块 `memcpy(data_size)` 拷入 `rgba_frame_->data[0]`，并把这个 Frame 的宽高设为固定编码目标 `width_/height_`。它没有按目标 Frame 的每行 `linesize` 逐行写入，也没有完整校验输入尺寸与存储大小。

因此“采集端已正确打包”与“编码输入支持任意尺寸和 stride”是两件事。当前 2560 宽的四字节行长为 10240，恰好与其 32 字节对齐相容；不能据此推广到任意分辨率。阅读时核对输入实际尺寸、转换器输入尺寸和 Frame 声明尺寸是否一致。

### 4.4 当前编码参数及其单位

主编排调用 `H264Encoder::OPen(2560, 1440, 30, 80000, BGRA)`：

| 内容 | 最终配置 |
| --- | --- |
| 编码尺寸 | `2560×1440` |
| 原始像素格式 | 转换前为 BGRA，送入 H.264 编码器的 Frame 为 YUV420P |
| 时间基、帧率字段 | `time_base={1,30}`，`framerate={30,1}` |
| GOP、B 帧 | `gop_size=30`，`max_b_frames=0` |
| 视频码率 | 封装层将 80000 乘 1000，最终 `bit_rate=80,000,000 bit/s`，即 80Mbit/s |
| 其他 | global header；尝试设置 `zerolatency / ultrafast` |

GOP 是一组连续图像，`gop_size` 以帧数配置图像组长度，用于控制关键帧间隔；它不是毫秒数，实际关键帧分布还受编码器策略影响。参数说明见 [AVCodecContext](https://ffmpeg.org/doxygen/8.0/structAVCodecContext.html)。

编码器由 `avcodec_find_encoder(AV_CODEC_ID_H264)` 和当前 FFmpeg 构建决定，不能仅凭 H.264 名称认定是某个硬件编码器；私有选项是否支持也取决于具体实现。B 帧可能引入呈现顺序与编码/解码顺序的重排；不使用 B 帧可减少这类等待，但不保证整个采编链没有延迟。

## 5. 音频：系统播放声音怎样成为 AAC

### 5.1 先认识 loopback 和 COM

WASAPI loopback 从 **render endpoint 的系统播放混音**取得声音。当前代码选默认 `eRender / eMultimedia` 端点，使用共享模式和 `AUDCLNT_STREAMFLAGS_LOOPBACK`；它不是默认麦克风采集，见 [Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)。

COM 接口是 Windows 提供这些设备能力的对象接口。使用它的线程需要相应初始化，并遵守所选线程模型；成功的初始化还要在相应线程配对 `CoUninitialize`。这与阶段四的 Winsock 使用期管理不同，不是某条线程初始化一次就替所有线程完成。

当前 `init()` 在调用线程执行 `CoInitialize(NULL)`，随后 `start()` 另建采集线程使用接口。未见采集线程的 COM 初始化，也未见对这些接口跨线程使用条件的处理，因此不能认定当前 COM 使用已安排完整。本阶段先指出创建、调用和清理各在哪个线程，相关停止与清理关系在阶段九核对。参见 [Initializing the COM Library](https://learn.microsoft.com/en-us/windows/win32/learnwin32/initializing-the-com-library)。

### 5.2 16 位 PCM 是请求格式，不是靠改字段转换样本

初始化顺序是：

```text
创建设备枚举器 → 选默认播放端点 → 激活 IAudioClient
  → GetMixFormat
  → adjustFormatTo16Bits
  → Initialize（shared + loopback）
  → GetService 取得 IAudioCaptureClient
```

`GetMixFormat` 提供设备混音格式。代码在 `Initialize` 前修改格式描述，意图请求 16 位 PCM，同时更新 `nBlockAlign / nAvgBytesPerSec`；这不是捕获后把 float 样本逐个转换成整数。

当前没有检查 `adjustFormatTo16Bits()` 返回值，也未见先调用 `IsFormatSupported`。请求能否采用，要看 `Initialize` 是否成功；采样率、声道数来自设备格式，不要把成员初值 48000、2 当成所有机器的实际结果。主编码入口则按 `AV_SAMPLE_FMT_S16` 配置后续处理。

### 5.3 GetBuffer 返回借用内存，普通路径在释放前复制

`capture()` 中的主要顺序：

```text
GetNextPacketSize
  → GetBuffer 得到 pData、numFrameAvailabel、flags
  → 同步调用 m_callback(format, pData, sampleFrames)
      → AudioCapture 回调
      → AudioBuffer::write 复制 nBlockAlign × sampleFrames 字节
  → ReleaseBuffer(sampleFrames)
```

`pData` 的有效期到对应 `ReleaseBuffer` 为止；回调不应只把这个裸指针保存给稍后使用。当前普通数据路径在释放前同步复制到自己的缓冲，见 [IAudioCaptureClient::GetBuffer](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer)。

需要单独识别静音分支：代码复制或清零的是 `m_pcmBuf`，但回调传入的仍是 `pData`。所以不能把“清零了自有缓存”解释成“上层已经收到相应静音样本”；静音标志要求按静音含义处理，而非继续依赖原指针内容。

### 5.4 PCM 缓冲按字节保存，编码按 sample frames 取

`AudioCapture::Init()` 默认创建 **20480 字节**的 `AudioBuffer`。它是带锁的有限字节缓冲，读出会复制并消费 PCM，再搬移未读数据以回收前缀空间。

`GetSamples()` 将可读字节数除以每个 sample frame 的字节数；`Read(samples)` 再做反向换算。管理器通过 `AACEncoder::GetFrames()` 取得编码器实际 `frame_size`，数据够一块才读出编码。不能仅凭 AAC 名称把该接口永远写成固定 1024。

例如设备为 S16、双声道，编码器要求 1024 sample frames：

```text
每次编码输入 = 4096 字节
20480 字节可容纳 = 5120 sample frames = 5 个这样的输入块
```

容量不足时 `AudioBuffer::write()` 截断到可写字节，调用方未检查实际写入量；可能丢 PCM，若截断未保持 sample-frame 边界，还会破坏排列。这不是已完成的背压机制。阶段四的流量控制概念可复用，这里只核对数据单位和实际策略。

### 5.5 S16 到 FLTP，以及当前 Frame 标签不一致

`AudioEncoder::Open()` 将 AAC 编码器接收的原始 PCM 格式设为 FLTP，压缩输出仍是 AAC Packet。`AudioResampler` 用 `swr_alloc_set_opts2` 设置：

```text
输入：设备采样率、声道数、S16 packed
转换输出：相同采样率、相同声道数、FLTP，交给 AAC 编码器
```

这里主要改变样本类型和排列，不一定改变采样率。`swr_get_delay` 与向上换算用于估计输出容量，实际输出样本数仍以 `swr_convert` 的返回值为准，不能把分配容量直接当有效样本数。参见 [libswresample](https://ffmpeg.org/doxygen/8.0/group__lswr.html)。

当前 `AudioEncoder::Encode()` 将输入 Frame 的 `format` 标为 FLT，却按配置的 S16 字节数复制 PCM，标签与真实数据不一致。这里 `memcpy` 只复制字节，整数到浮点的转换由后续重采样完成。实际调用的 `swr_convert` 按 SwrContext 中配置的输入格式解释数据；它接收的是数据指针，不会根据这个 Frame 的 format 字段改成按 FLT 读取。

### 5.6 音频码率不能照参数名解释

`AACEncoder::Open(..., bitrate_kbps)` 收到管理器传入的 64 后，直接传入配置，`AudioEncoder` 又直接赋给 `AVCodecContext::bit_rate`。

这个字段单位是 bit/s，当前链路没有乘 1000，所以源码实际请求的是 **64bit/s，而不是 64kbit/s**。应核对最终字段和编码器返回，不能用参数名或调用注释代替单位检查。它与第 4.4 节 `H264Encoder::OPen()` 的乘 1000 行为不同。

## 6. 编码参数和输出怎样交给发布接口

### 6.1 SPS/PPS 与 AAC 配置是什么

| 内容 | 本阶段需要知道的用途 |
| --- | --- |
| H.264 SPS/PPS | 解码所需的序列/图像参数，NAL 类型分别为 7、8 |
| 起始码 | Annex B 中的 NAL 分界标记；不同于 NAL 数据本身 |
| AAC AudioSpecificConfig | 描述 AAC 配置，和每帧音频数据、ADTS 头分开理解 |
| `AV_CODEC_FLAG_GLOBAL_HEADER` | 本项目据此从编码上下文 `extradata` 获取配置 |
| `MediaInfo` | 持有复制后的参数，交给 Publisher 构造媒体配置消息 |

当前 `H264Paraser::findNal` 按 Annex B 起始码查找，说明项目对 extradata 布局有相应假设，不能把任意编码器的 extradata 都直接套用这种解析。

### 6.2 局部配置数组不会直接变成悬空参数

`Init()` 使用局部 `extradata[1024]` 取参数，从中寻找 SPS/PPS，并分别复制到 `MediaInfo` 的独立数组；AAC 配置也复制到独立数组。`SetMediaInfo` 保存共享持有并构造自己的序列头，因此局部数组结束不使这些副本失效。

读取时还要核对长度：视频 `GetSequenceParams()` 没使用传入容量作边界检查；音频 `GetSpecificConfig()` 返回有符号结果，编排层用无符号变量接收且未先检查成功长度。缓冲区存在，不代表复制长度已经有效。

### 6.3 编码数据的交接边界

视频 `H264Encoder::Encode()` 根据 `AV_PKT_FLAG_KEY` 识别关键包，在关键包前复制 extradata，再把 Packet 数据复制到输出 vector。音频则返回一个 AAC Packet，管理器在当前调用中读取其 `data / size`。

随后 `PushVideo / PushAudio` 再复制数据并调用 Publisher。当前视频入口固定去掉前 4 字节，不能概括为通用的 Annex B 转换；多 NAL、起始码长度及具体媒体封装在阶段七继续检查。

本阶段追到“输出哪些字节、由谁持有、交给哪个接口”即可，编码 Packet 已产生也不代表媒体已经发出或被对端解码。

## 7. 对照项目中的三套时间

### 7.1 采集与调度间隔不等于编码时间基

| 位置 | 当前含义 |
| --- | --- |
| gdigrab `framerate=25` | 设备采集配置 |
| 屏幕 `run()` | 每轮额外休眠 `1000/25=40ms` 后再读帧 |
| `EncodeVideo` 的 `fameRate=30` | 实际用作毫秒 delay，理想间隔约 30ms，不是 30fps |
| 编码器 `time_base=1/30` | PTS 的时间单位，不控制线程调度 |

采集、等待和编码本身都耗时，不能由配置值推断实测帧率。最新帧机制还会导致重复或跳帧，不能仅按编码调用次数还原每张图像的真实采集时刻。

### 7.2 当前视频 PTS 没有自动递增

[VideoEncoder.h](../Codec/VideoEncoder.h) 的参数是 `quint64 pts = 0`，而实现使用：

```cpp
out_frame->pts = pts >= 0 ? pts : pts_++;
```

无符号值满足 `pts >= 0`，自动计数分支不会执行；当前上层又未传 PTS，所以默认路径每帧都使用 0。不能将成员 `pts_` 的存在解释为已经按帧递增。

如果正常按 `time_base=1/30` 计数，连续帧的 PTS 可为 0、1、2……；这是解释时间基的算例，不是当前代码已经实现的行为。

### 7.3 音频计数与发布毫秒又是两条路径

音频 `pts_` 按累计输入 sample frames 增长，以 `{1, sample_rate}` 为源时间基，经 `av_rescale_q` 转到实际编码器时间基。若采样率 48000、每块 1024，输入计数为 0、1024、2048……，对应约 0、21.33、42.67ms；重采样输出沿用该 PTS。

这不是设备时间戳：当前 WASAPI `GetBuffer` 的设备位置和 QPC 输出参数传了空指针。

发布层 [RtmpPublisher.cpp](../Pusher/rtmp/RtmpPublisher.cpp) 则使用 [Timestamp::Elapsed()](../Net/TimeStamp.h) 的运行时长毫秒，未直接把编码 Packet 的 PTS/DTS 换算传下去。因此视频 PTS、音频输入计数和发布时钟要分别追踪，不能据此认定音画已经对齐。同步策略在后续媒体与联调阶段继续核对。

## 8. 数据寿命与本阶段的释放边界

### 8.1 结构、缓冲和引用分别由谁管理

| 对象或数据 | 当前持有和有效期 |
| --- | --- |
| WASAPI `pData` | 系统借用数据，到对应 ReleaseBuffer 前；普通路径已同步复制 |
| 采集解码 Frame | 自定义删除器调用 `av_frame_free`；图像复制后用 unref 释放本次数据引用 |
| 采集“最新图像”与 CaptureFrame 输出 | 独立堆内存和 vector 副本，不借用已 unref 的解码数据 |
| 转换输出 Frame | 每次分配，FFmpeg 引用计数缓冲；局部智能指针释放不等于编码器持有的引用一并消失 |
| 视频 Packet | `VideoEncoder` 返回复用的成员 Packet；复制 shared_ptr 只共享同一个对象，不是数据快照 |
| 音频 Packet | 每次 Encode 新建，由 `av_packet_free` 自定义删除器管理 |
| `MediaInfo` 参数 | 独立复制后共享持有，不借用局部 extradata 数组 |

`AVFramePtr / AVPacketPtr` 只是 C++ 类型别名，正确释放还依赖构造时设置的 FFmpeg 删除器。`unref` 释放数据引用、保留可复用结构；`free` 还释放结构。需要独立保存跨次接收的 Packet 时，应区分 `av_packet_ref / clone` 与共享同一个 C++ 指针，见 [AVPacket](https://ffmpeg.org/doxygen/8.0/structAVPacket.html)。

官方编码示例还会在复用并改写 Frame 数据前检查 `av_frame_make_writable`。本项目的转换输出每次新分配，不能把不同的分配/复用方式混为一谈。

### 8.2 Close 的名称不等于已释放全部资源

管理器当前先设置退出标志、处理发布连接，再由 `StopEncoder` 等待两条编码线程并关闭编码器，最后 `StopCapture` 关闭音频与屏幕采集。

屏幕自定义 `run()` 通过 `stop_` 条件退出，并由 `wait()` 等待；`quit()` 本身不能替代这个循环条件。其他关键释放点需要分开看：

| 资源 | 应认识的释放接口与当前代码 |
| --- | --- |
| 编码上下文 | 底层 `VideoEncoder::Close/AudioEncoder::Close` 不直接释放 codec context；还要继续追封装层 reset 和 `EncodBase` 析构中的 `avcodec_free_context`，不能把底层 Close 等同于整条销毁路径 |
| 图像转换上下文 | `VideoConverter::Close → sws_freeContext` |
| 音频转换上下文 | 应区分 `swr_close` 与 `swr_free`；当前 Close 仅 close 后置空，存在分配释放缺口 |
| 设备格式 `m_mixFormat` | GetMixFormat 分配，需 `CoTaskMemFree`；当前未见配对释放 |
| COM 接口 | `ComPtr` 在释放持有时调用接口 Release，不代替格式内存释放或线程 CoUninitialize |
| COM 使用期 | `AudioCapture::Close` 只停采集，未调用 `WASAPICapture::exit`；当前清理路径并不完整 |

设备格式的释放要求见 [GetMixFormat](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getmixformat)。这些内容用于分清资源类别和实际路径；跨线程访问、部分初始化失败和重开顺序留阶段九统一检查，不把修完全部问题作为继续学习的条件。

## 9. 按视频、音频分别完成局部学习

1. 先读官方视频编码示例中“填 Frame → send → 循环 receive → 正常 drain”的代码，对照本讲第 2 节理解格式与字段。有现成可运行示例时观察一次输入和输出，不要求另建示例工程。
2. 回到视频路径，核对采集实际 format/width/height/linesize、转换输入输出、编码参数和 Packet。先把这一条追通，再按同样方法读音频。
3. 音频先算一块 PCM 的样本数、字节数和时长，再看借用数据何时复制、何时转换成 FLTP、如何取得编码器 frame_size。
4. 最后把视频 PTS、音频输入计数与发布毫秒分别追到赋值位置，结合第 8 节确认关键数据的有效期。

已有局部采集/编码调试条件时，可任选一条观察：视频在解码得到 Frame 后查看实际格式与 linesize，再看转换输出；音频在同步回调中查看设备格式和 sample frames，再看进入编码器的 Frame。条件不足时，完成行跨度、4096 字节 PCM 和时间基的推演即可。

`RtmpPushManager::Open()` 先启动采集，再连接媒体服务，随后启动编码线程，不适合作为本阶段的最小独立编码实验。完整推流与双端验收继续复用 ENET [阶段十二](https://github.com/slimesq/ENET/blob/main/docs/项目学习规划.md#stage-12)。

## 10. 自查与下一步

结合源码回答：

1. 当前采集为何应看 Frame::format，而不能凭 rgba 变量名认定 RGBA？linesize 怎样影响复制？
2. 最新帧保存与逐帧队列有什么区别，采集线程和编码线程各在哪里启动？
3. S16 双声道 1024 sample frames 是多少字节？WASAPI 指针释放前谁完成复制，静音分支有什么缺口？
4. S16 到 FLTP 改变了什么？输入 Frame 标签、SwrContext 配置和实际字节是否一致？
5. 视频 80000、音频 64 最终各是什么码率单位？没有输出 Packet 时为什么不能一概判失败？
6. 当前视频 PTS、音频计数与发布时钟分别怎样产生？参数副本、Frame/Packet 和转换上下文怎样释放？

- [ ] 能从实际格式、尺寸和行跨度追到 YUV420P、H.264 输出。

- [ ] 能解释 send/receive、EAGAIN 和正常 drain，并对照当前实现的简化。
- [ ] 能区分三套时间及码率单位，指出实际赋值与关键缺口。
- [ ] 能说明采集/编码线程的交接和关键资源的持有、复制与释放位置。
