# ECloudAssistant 项目学习规划

> 目标：能够独立解释客户端及其配套服务端的主要业务链、数据格式、线程、对象所有权、失败路径和退出顺序，并能用源码与运行观察验证自己的解释。
>
> 组织方式参考 [IOCP 项目的学习路线](../../edoyun/IOCP/docs/IOCP学习路线.md)：先建立可运行基线，再沿真实调用链逐层学习；每阶段都以可复述的结论和小练习验收。

## 1. 先明确学习范围

当前仓库的主目标是 Windows 桌面程序 `ECloudAssistant`，使用 C++17、Qt、FFmpeg、Winsock、Windows 屏幕与音频接口，以及 OpenGL。主程序同时包含被控端推流和控制端拉流、输入发送的代码。

用户提供的 `GOICDZDYLMRXH9QB_20250515144010A008.rar` 中有另一个源码根目录 `ENET/`，现已迁移到与当前仓库并列的 [`ENET` 工程](../../ENET/README.md)。其中的 `LoadBanceServer`、`LoginServer`、`SigServer`、`RtmpServer`，连同 Linux 网络库 `EdoyunNet`，从协议命令和服务职责看，是当前客户端的**配套服务端候选源码**。公共库及四个服务已在 Linux 上编译通过；登录服务的构建验证使用了临时解包的 MariaDB 开发文件，尚未做运行和端到端兼容性验证。本规划后半部分把它纳入学习范围；下文的 `ENET/...` 路径均指该独立工程中的路径。

| 范围 | 当前源码位置 | 学习时要回答的问题 |
| --- | --- | --- |
| 构建与入口 | [`CMakeLists.txt`](../CMakeLists.txt)、[`CMakePresets.json`](../CMakePresets.json)、[`main.cpp`](../main.cpp) | 哪些文件真正进入程序？依赖和运行环境从哪里来？ |
| 界面与业务编排 | [`ECloudAssistant.cpp`](../ECloudAssistant.cpp)、[`UI/`](../UI/) | 登录、远程连接、推流和拉流怎样被界面触发？ |

## 2. 学习方法与完成标准

每读一个功能，固定追踪六件事：

1. **入口**：用户动作、网络事件或线程回调从哪里进入？
2. **数据**：输入、输出、协议包、音视频帧的格式和单位是什么？
3. **线程**：函数实际在哪个线程执行？跨线程靠什么交接？
4. **所有权**：socket、QObject、FFmpeg 对象、帧和缓冲区由谁持有？
5. **状态**：哪些状态允许操作，成功、失败、断线后如何转移？
6. **证据**：结论来自源码、调试运行，还是仍待验证？

每阶段采用“先画图 → 沿调用链读代码 → 用断点或日志核对 → 做一个小实验 → 不看源码复述”的闭环。笔记中给每条结论标记 `源码证实`、`运行证实` 或 `待验证`。读到可疑实现时先记录触发条件与预期行为，不把注释当作运行结果。

最终完成不是记住全部函数名，而是能够：

- 从两端启动到负载选择、登录、被控端加入信令、控制端申请流、推拉流和输入控制，分别画出完整时序图。
- 手工解释主要协议包字段及 TCP 半包、粘包、部分发送时的处理过程。
- 画出 GUI、客户端网络调度、服务端 `epoll` 调度、采集编码、解封装解码、播放线程之间的交接图。
- 列出关键资源的创建者、使用者、关闭者，以及连接失败和退出时的路径。
- 对每条链说明已验证的行为、客户端与 `ENET` 源码的对应关系，以及尚待联调验证的假设。

### 阶段 0：建立可复现的基线

**阅读顺序：**[`CMakeLists.txt`](../CMakeLists.txt) → [`CMakePresets.json`](../CMakePresets.json) → [`.vscode/settings.json`](../.vscode/settings.json) → [`main.cpp`](../main.cpp) → [`res.qrc`](../res.qrc)。

**任务：**

- 说明为什么这是 Windows 目标，Qt 与 FFmpeg 各链接了哪些组件。
- 找出 `file(GLOB...)` 收集的源码和明确排除的 `Net` 演示文件。
- 在 Visual Studio 开发环境中检查 Ninja、Qt、FFmpeg 的配置；预设依赖 `NINJA_EXE`，Qt 可由 `QTDIR` 定位，FFmpeg 可由 `FFMPEG_HOME` 或 `FFMPEG_INCLUDE`、`FFMPEG_LIB` 定位。
- 在环境具备时执行 `cmake --preset msvc-debug` 和 `cmake --build --preset msvc-debug`，记录工具版本、构建结果和可执行文件位置。现有构建产物只说明曾经编译过，不能代替本人的基线记录。

**验收：**不看 CMake 文件，说明主程序入口、构建目标、依赖和未参与构建的文件。不要用“编译成功”推断远控链已经可用。

### 阶段 1：只补项目真正用到的基础

**C++：**RAII、`unique_ptr` / `shared_ptr`、引用与裸指针、`std::thread` / `join`、`mutex` / `atomic`、lambda 捕获、二进制结构体布局。结合 [`AV_Common.h`](../Codec/AV_Common.h)、[`AV_Queue.h`](../Codec/AV_Queue.h)、[`TcpConnection.h`](../Net/TcpConnection.h) 学习。

**Qt：**`QObject` 的 parent、signal/slot、`QApplication` 事件循环、`QStackedWidget`、`QTcpSocket::readyRead`、跨线程 queued 调用。结合 [`MainWgt.cpp`](../UI/center/MainWgt.cpp)、[`LoginWgt.cpp`](../UI/center/LoginWgt.cpp)、[`AVPlayer.cpp`](../Puller/UI/AVPlayer.cpp) 学习。

**媒体与平台：**先理解 `AVPacket` 与 `AVFrame`、时间基、像素格式、PCM 采样格式、H.264 的 SPS/PPS 和 AAC 配置，再接触 FFmpeg API；了解 Windows `SendInput`、WASAPI、FFmpeg `gdigrab` 和 OpenGL 纹理的职责。此阶段只建立术语，不需要预先精通所有 API。

**验收：**任选一个 `shared_ptr<AVFrame>` 和一个 socket，说明它们何时创建、最后一次使用发生在哪里、由谁释放。说明 GUI 线程与 `std::thread` 的区别。

### 阶段 9：并发、资源关闭与失败路径

### 阶段 14：协议对照、端到端实验与最终验收

先做一张**客户端 / 服务端兼容矩阵**：命令编号、包头布局、字段顺序、结构体大小、字符串终止、IP 与端口、RTMP 流路径、两端错误码。至少核对以下已发现的差异：客户端负载入口写为 `192.168.31.30:8523`，服务端的实际监听地址写为 `172.21.205.121`；服务端分别监听 8523、9867、6539、1935；输入事件结构体在两份定义中的字段顺序与有符号性需要逐项比较。配置修正与协议兼容性必须先确认，再进行运行验证。

在具备可构建、地址一致且协议匹配的服务端时，先记录两端版本与配置，再按顺序验证：

1. 只启动客户端，确认界面入口、页面切换和没有服务时的错误路径。
2. 验证负载入口和登录结果，记录每次请求、响应及信令地址来源。
3. 用两个客户端验证被控端加入、控制端申请流、被控端推流和控制端播放。
4. 分别验证鼠标移动、按下/释放、键盘按下/释放和滚轮；记录控制端事件到被控端执行的日志或断点证据。
5. 验证断线、重复连接、推拉流失败和退出；观察线程、socket、FFmpeg 与 Qt 对象是否按预期收尾。

如果服务端暂时不可运行，可先完成静态时序图、协议包样例和本地媒体链实验，并将服务端运行结果标为 `待验证`。不要把压缩包中的旧构建产物当作本次联调证据。

**最终交付物：**一张双工程模块依赖图、四张端到端时序图（登录、远控建流、媒体分发、输入事件）、一张双端线程和资源所有权表、一份协议兼容矩阵、一份成功/失败/退出路径矩阵，以及一段不看源码的完整讲解。讲解应能从用户点击开始，持续追踪到负载、数据库、信令、采集、编码、RTMP 服务、解码、显示和远程输入。
