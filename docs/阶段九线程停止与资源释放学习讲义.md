## 2. 先分清停止、等待与销毁

### 2.1 一个停止标志只是一条请求

以循环中检查标志为例，停止方写入 true 后，工作线程还可能正在采集、编码、写入或执行回调；它需要从当前操作返回，再检查标志并退出。

| 动作 | 能说明什么 | 不能据此认定什么 |
| --- | --- | --- |
| 设置退出标志 | 已请求相关循环退出 | 线程已经停止、阻塞调用已返回 |
| `std::thread::join()` | 成功返回后，被等待线程已结束 | 它会主动终止线程，或其他线程也已结束 |
| `QThread::wait()` | 等待对应线程结束；应确认返回结果 | QObject 已换线程或对象已被删除 |
| `QThread::quit()` | 请求线程中的 Qt 事件循环退出 | 能停止任意自定义 run 循环 |
| reset 智能指针 | 释放当前指针持有的所有权 | 工作线程已退出，其他裸指针已被清空或不会再访问对象 |
| 关闭窗口 | 触发窗口关闭流程 | 播放、网络与采集均已停止 |

`joinable()` 表示线程对象仍关联一个可等待的线程，不是“线程现在仍在运行”。线程函数已经返回但尚未 join 的对象，也可能 joinable；销毁仍 joinable 的 `std::thread` 会调用 `std::terminate`。`detach()` 只解除线程对象的关联，不会解决工作线程继续访问已销毁对象的问题。

`join()` 成功返回还建立该线程完成与调用者继续执行之间的同步关系；它不会补救线程运行期间已经发生的数据竞争。规则参见 C++ 标准草案的 [join/joinable](https://eel.is/c++draft/thread.thread.member) 与 [thread 析构](https://eel.is/c++draft/thread.thread.destr)。

### 2.2 标志、数据与对象寿命需要分别保护

本项目中要分开看三件事：

1. **退出标志怎样同步。** 一个线程写普通 bool，另一个线程无同步地读，会形成数据竞争；sleep 不提供同步。独立退出标志可用 atomic，关联状态则需要相应锁或其他明确的同步协议。
2. **共享数据怎样交接。** 队列 push/pop 加锁，不代表 `empty()/size()`、退出标志和对象指针也受同一把锁保护。
3. **对象活到什么时候。** 即使标志同步正确，也不能在线程结束前释放它仍会使用的对象。

shared_ptr 同样有边界：不同 shared_ptr 实例可以共享同一控制块，但并发读取与 reset **同一个成员 shared_ptr** 仍需同步；其引用计数也不会给被指向对象的成员加锁。`[this]` 只保存一个裸指针，不会延长对象寿命。有关数据竞争的定义见 [C++ 标准草案](https://eel.is/c++draft/intro.races)。

因此，“把所有标志改为 atomic”不能同时解决 Publisher 被提前 reset、裸回调悬空，以及在错误线程清理设备等问题。

### 2.3 等待顺序由依赖决定

`join` 之前，应先让目标线程具备退出条件；`join` 之后，才能释放只由该线程使用、且已无其他使用者的资源。

判断顺序时问三句即可：

- 线程退出前还会访问谁？这些对象此时必须仍在。
- 它是否正等待某个调用、锁或回调？停止方有没有让这次等待结束？
- 执行 join 的是不是目标线程本身？是否持有目标线程退出时需要的锁？

例如“关闭方持有锁 M 并 join，工作线程退出前也要取得锁 M”，会形成相互等待。但不能仅看到持锁 join 就断定存在这条依赖。

自 join 也需要具体调用路径：当前信令线程等待采编线程，等待的是其他线程；若在某 EventLoop 自己的工作线程中同步退出该 EventLoop，再 join 自己，就不满足 join 条件。

项目沿用 C++17 的 `std::thread` 与现有 Qt API，不需要为本阶段改用另一套线程框架。

## 3. 从哪些入口停止，由谁持有对象

### 3.1 先区分四种入口

| 入口 | 当前路径 | 执行位置与边界 |
| --- | --- | --- |
| 信令通知停止 | `doDeleteStream` 在 `streamCount == 0` 时直接调用已设置的回调；RemoteManager 绑定 `RemoteManager::HandleStopStream`，AVPlayer 绑定 `AVPlayer::HandleStopStream` | 在网络调度线程同步执行；其中 join 会阻塞该线程 |
| 信令连接关闭 | `TcpConnection::Close → SigConnection::OnClose` | OnClose 只设置自己的 `quit_`，没有调用停止媒体的回调 |
| 拉流窗口关闭 | QWidget 的关闭流程 | 当前没有接到播放器 Close；隐藏与停止的区别见第 7.2 节 |
| 对象销毁 | `~RemoteManager → Close`；`~AVPlayer → Close`，随后继续析构成员和基类 | 通常由 GUI 销毁控件；还要跟成员声明顺序，不能停在析构函数体 |

停止回调是 `std::function`，分别捕获 `RemoteManager/AVPlayer` 的裸 this。它不是 Qt queued connection，不会因目标继承 QObject 就切到 GUI，也不享有 Qt signal 自动断开的那套管理。

因此不能把“信令 TCP 关闭”与“业务媒体已停止”画成当前代码里已经接通的同一条链。

### 3.2 两条 EventLoop 与对象持有关系

```text
RemoteWgt
  └─ unique_ptr<RemoteManager>
       ├─ unique_ptr<PullerWgt>
       │    └─ unique_ptr<AVPlayer>
       │         ├─ shared_ptr<SigConnection>
       │         ├─ unique_ptr<AVDEMuxer>
       │         ├─ 两个输出线程对象
       │         └─ AVContext*（raw new）
       ├─ unique_ptr<EventLoop> event_loop_（信令）
       └─ shared_ptr<SigConnection>（被控端信令）

RemoteManager 的基类 RtmpPushManager
  ├─ EventLoop* loop_（另一个媒体循环，raw new）
  ├─ shared_ptr<RtmpPublisher> → shared_ptr<RtmpConnection>
  ├─ 两个采编发送线程对象
  └─ 编码器与采集器
```

`RemoteManager::event_loop_` 与基类 `RtmpPushManager::loop_` 是两个独立对象。停止前者不会自动停止后者；基类这条 raw new 的媒体循环未见对应 delete 或 Quit。

连接保存的 `TaskScheduler*`、播放器保存的 `EventLoop*`、解码器保存的 `AVContext*` 都是借用关系。判断它们能否使用，必须回到实际持有者，不能从裸指针推断所有权。

## 4. 推流停止：先看真实顺序，再判断资源能否释放

### 4.1 RtmpPushManager::Close 的当前顺序

```text
exit_=true，isConnect=false
  → 若 pusher_ 存在且 IsConnected()
      → RtmpPublisher::Close
      → reset pusher_
  → StopEncoder
      → join audioCaptureThread_
      → join videoCaptureThread_
      → Close/reset H264Encoder
      → Close/reset AACEncoder
  → StopCapture
      → AudioCapture::Close/reset
      → GDIScreenCapture::Close/reset
```

`audioCaptureThread_/videoCaptureThread_` 的名称容易误导：它们实际执行 `EncodeAudio/EncodeVideo`，负责读取采集结果、编码和提交发送。底层 WASAPI 与 GDI 采集还有自己的线程，不会随这两个 join 自动结束。

若 Publisher 已存在但 `IsConnected()` 为 false，当前条件分支不会 Close/reset 它；不能把图中的条件步骤当成所有情况下都会执行。

### 4.2 为什么先 reset Publisher 有问题

采编线程的 `PushAudio/PushVideo` 仍会读取 `pusher_`、检查连接并调用发送。退出请求发出时，它们可能已经进入一轮处理，还未回到 while 条件。

当前先 Close/reset `pusher_`，再 join 使用它的线程，缺少覆盖该成员访问的同步。`if (pusher_)` 检查不构成保护；同一个成员 shared_ptr 被并发读取与 reset，本身就可能形成数据竞争。

应从依赖得出顺序要求：停止新的采编发送，并确认已有发送调用不再访问 Publisher，再释放 Publisher 和编码器。若为了退出要先关闭连接，也必须保证对象保持存活、关闭与发送有明确同步，不能把“提前释放对象”当成解除等待的手段。

这里需要理解的是资源必须晚于使用者释放，不是规定任何程序都必须“先音频、后视频”。当前两个 join 的排列来自源码。

### 4.3 底层采集怎样停止，回调还会访问谁

| 组件 | 当前停止动作 | 必须继续存活的对象 |
| --- | --- | --- |
| `AudioCapture` | Close 调用 StopCapture，再调用底层 `stop()` | 捕获回调使用的 AudioCapture、格式字段和 AudioBuffer |
| `WASAPICapture` | 持有 `m_mutex`，将 `m_isEnabeld=false`，join 内部线程，再 `IAudioClient::Stop` | WASAPI 对象、COM 接口、PCM 数据和回调目标 |
| `GDIScreenCapture` | Close 调用 `StopCapture()`：设置 `stop_`，若在运行则 quit/wait；随后清理最新画面，Close 再释放输入和解码上下文 | 采集对象、Frame 与 FFmpeg 上下文 |

WASAPI 回调捕获 `AudioCapture` 的 this，并写入 `audio_buffer_`。先销毁缓冲区，再希望回调自行停止，不满足对象寿命要求。正常顺序应先等采集线程不再调用回调，再销毁缓冲区和目标对象。

WASAPI 的停止方持有 `m_mutex`，但当前采集循环和该回调并不取得这把锁，不能直接宣称它必然发生第 2.3 节的持锁等待死锁。当前首先要注意的是 `m_isEnabeld` 为普通 bool，采集循环读取它时没有相同同步。

GDI 的 run 自己轮询采集，没有 `exec()`；决定退出的是 `stop_`，不是 quit。若它停在 FFmpeg 读取内部，还要检查读取能否返回；当前没有像播放器那样设置输入中断回调，不能承诺 wait 会立即完成。QThread 的规则见[官方文档](https://doc.qt.io/qt-6/qthread.html)。

### 4.4 当前退出标志的实际保护

| 对象 | 状态 | 当前类型或边界 |
| --- | --- | --- |
| `RtmpPushManager` | `exit_/isConnect` | 普通 bool，关闭方与采编线程间未形成统一同步 |
| `GDIScreenCapture` | `stop_` | 普通 bool；画面数据的锁不等于退出标志也已受保护 |
| `WASAPICapture` | `m_isEnabeld` | 普通 bool；start/stop 的锁没有覆盖采集线程的全部读取 |
| `AVPlayer` | `stop_` | 普通 bool，由关闭方写、输出线程读 |
| 两个解码器 | `quit_` | 普通 bool，由 Close 写、run 读 |
| `AVDEMuxer` | `quit_` | atomic bool，供读包循环和中断回调读取 |
| `TaskScheduler` | `is_shutdown_` | atomic bool，供调度主循环检查 |

这张表只说明标志本身。atomic 的存在不代表该对象的字典、指针、回调和所有资源都已被同步保护。

## 5. 播放停止：消费、读包与解码要分别等待

### 5.1 AVPlayer 到解码器的完整顺序

```text
AVPlayer::Close
  → stop_=true
  → join audioThread_，销毁该线程对象
  → join videoThread_，销毁该线程对象
  → reset avDEMuxer_
      → AVDEMuxer 析构体调用 Close
          → atomic quit_=true
          → 释放 avDict_
          → join readthread_
          → avformat_close_input
      → h264Decoder_ 成员析构
          → quit_=true → 若在运行，quit()/wait()
      → aacDecoder_ 成员析构
          → quit_=true → 若在运行，quit()/wait()
```

两个解码器的析构顺序来自 `AVDEMuxer.h` 的成员声明逆序，不是因为视频必须先于音频。它们的 codec context 已从流参数复制建立，因此不应把 FFmpeg 输入上下文和解码上下文当成同一个对象。

当前先停输出，再停读包和解码。因此 join 输出线程后，上游仍可能短暂产生 Frame；这条 Close 路径不是正常 EOF 后把全部尾部播放完的流程。正常读完与主动停止的区别复用阶段八。

### 5.2 阻塞读流怎样有机会返回

`AVDEMuxer` 将 `AVFormatContext::interrupt_callback` 指向 `InterruptFouction`，opaque 保存 this。回调返回 `quit_`：

```text
关闭方设置 quit_=true
  → FFmpeg 在相关阻塞操作中检查中断回调
  → 回调返回 1，相关操作中止
  → 读包线程返回
  → join 返回
  → 才能释放该线程仍可能使用的输入资源
```

设置标志并不是向线程发送强制终止指令，也不保证任意库调用立即返回。中断检查依赖相关 FFmpeg 操作的实现，语义见 [AVIOInterruptCB](https://ffmpeg.org/doxygen/8.0/structAVIOInterruptCB.html)。

opaque 指向的 AVDEMuxer 必须在回调可能执行期间存活；输入上下文也不能在读取尚未结束时释放。

当前输入上下文在 join 后关闭，方向正确；但 `avDict_` 在 join 前已释放。如果读线程还处于使用该字典打开输入的阶段，就缺少安全的寿命保证。打开失败与刚开始就停止时，也要沿同一条关系检查。

### 5.3 QThread 的 wait 不会替你结束自定义循环

两个解码器的 run 都是“检查退出标志 → 看 Packet 队列 → 解码转换”的循环，没有运行 Qt 事件循环。

因此：

- quit 不会直接结束这段循环；它需要看到自己的退出条件，或从错误分支返回。
- wait 等待 run 结束，不会让普通 bool 的跨线程读写自动变得安全。
- 解码器必须在其 run 退出后再销毁转换器、Packet 队列与 codec context。
- wait 不会改变 QThread 对象本身的线程归属。

这两个 QThread 对象在 GUI 构造路径创建，属于 GUI 线程；run 则在各自的工作线程执行。通过信令回调直接 reset demux 时，当前代码却从网络调度线程删除这些对象。wait 成功只说明工作线程已结束，不改变对象的线程归属；最终删除仍应安排到 GUI 线程，并保证所需事件能够得到处理。规则见 [QObject 文档](https://doc.qt.io/qt-6/qobject.html)。

### 5.4 两级队列清完，也未必没有 Frame 持有者

`AVContext` 必须至少活到读包、解码和输出线程都不再访问它。当前由 raw new 创建，未见对应 delete；不能用“输出线程已 join”解释为它已被清理。

解码器销毁时，其 Packet 队列成员会 clear，释放其中的 shared_ptr 引用。Frame 队列在 AVContext 中，不随 demux 自动销毁；已经出队的视频 Frame 还可能被 GUI 事件持有。clear 一个队列也只释放该队列的引用，其他持有者仍可保留数据。

`videoPlay` join 后，只是不会再产生新的 `sig_repaint`。已排队的 GUI 槽仍可能执行，且 `Repaint` 当前没有检查 stop，所以停止后仍可能出现一次或多次页面更新。这不是输出线程仍在运行的证据，应查事件是否已经在停止前投递。

## 6. 网络停止：逻辑关闭、注销、句柄与调度线程

### 6.1 TcpConnection::Close 没有完成所有清理

复用阶段四，当前主要过程为：

```text
DisConnect（先取得连接 mutex）
  → Close（仅在尚未关闭时执行以下主体）
      → is_closed_=true
      → task_schduler_->RmoveChannel(channel_)
      → 若 closeCb_ 已设置，调用 closeCb_(shared_from_this())
      → 若 disconnectCb_ 已设置，调用 disconnectCb_(shared_from_this())
```

Close 没有等待发送缓冲排空，也没有直接调用 closesocket；后者在连接析构函数中尝试执行，当前判断为 `fd > 0`。

[TaskScheduler.h](../Net/TaskScheduler.h) 中，虚函数 `RmoveChannel` 的函数体为空；[SelectTaskScheduler.h](../Net/SelectTaskScheduler.h) 声明的则是 `RemoveChannel`。两者名称不同，派生类没有覆盖基类函数，因此当前关闭调用执行的是基类的空实现，未执行派生类中实际移除事件的逻辑。

关闭回调在上述连接锁内同步执行。若回调再次调用需要同一把锁的连接方法，就要检查重入等待；不能把普通回调当成另一个线程稍后执行的任务。

### 6.2 Channel 活着，不等于连接活着

```text
调度器 channels_ / 本轮 event_list
  → shared_ptr<Channel>
      → IO 回调 [this]
          → TcpConnection（裸指针目标）

业务持有者
  → shared_ptr<TcpConnection>
```

调度表与本轮事件列表保住的是 Channel，没有因此保住连接。即使将来修正了移除函数，本轮已收集的事件仍可能暂时持有 Channel；释放连接前还要确认没有正在执行或仍可进入的回调。

业务回调参数中的 shared_ptr 可以在这次回调期间保持连接存活，前提是调用 `shared_from_this()` 时对象仍然有效；它不能让一个已悬空的 this 重新获得所有权。这份强引用也不会延长回调所捕获的 RemoteManager、AVPlayer 裸指针目标的寿命。

因此要分别检查“连接是否存活”和“外层回调目标是否存活”。当前事件注销缺口会影响前者，普通裸 this 回调会影响后者；这些是需要满足的条件，不代表每次关闭都必然崩溃。

### 6.3 RTMP 收尾与本地关闭不能互相代替

`RtmpPublisher::Close` 暂存一份连接 shared_ptr，清空成员 `rtmp_conn_`，再调用 `DisConnect`。局部强引用保证这次调用期间连接不因清空该成员而立即销毁；它不负责其他线程对同一个成员的同步。

之后 `RtmpConnection::OnClose` 虽然调用 DeleteStream，但 `TcpConnection` 已先设置关闭标志；`SendInvokeMsg` 会因 IsClosed 拒绝发送。因此不能用这条路径上的 DeleteStream 返回值，证明服务端已收到删除流命令。

`RtmpConnection` 对 Publisher 的反向 weak_ptr 避免反向强持有，但它不会自动保护 Channel 的裸 this，也不会管理外层 GUI 对象的回调。

### 6.4 EventLoop::Quit 等什么

```text
EventLoop::Quit
  → 对所有 TaskScheduler 调用 Stop
      → atomic is_shutdown_=true
  → 逐个 joinable 检查并 join 工作线程
  → clear 调度器与线程对象容器
```

Stop 只发请求。正在执行的定时器和 IO 回调仍须返回，调度循环才能再次检查标志。当前 select 使用 `timeval{0, 0}`，是立即返回的轮询，不是通过额外唤醒 fd 解除阻塞。

还要检查刚启动就退出的时序：`TaskScheduler::Start()` 开头会把 `is_shutdown_` 重置为 false；若 Stop 早于工作线程真正进入 Start，停止请求可能被覆盖。atomic 只保证该变量的原子读写，不保证启动与停止的先后顺序已经协调好。

Quit 未检查调用者是否就是被等待的工作线程。只有在这种调用路径下才形成自 join 风险，不能把正常 GUI 析构或信令线程等待采编线程都称为自 join。

调度器结束不代表所有连接对象已关闭；连接又借用调度器指针，不能在后续仍可能 Send/DisConnect 时先销毁调度器。安全顺序要同时满足“连接关闭需要调度器有效”和“连接销毁前回调不能再进入”。

## 7. 外层对象与系统资源怎样真正释放

### 7.1 RemoteManager 的实际析构顺序

C++ 先执行派生类析构函数体，再按声明逆序销毁其成员，最后销毁基类。当前为：

```text
RemoteManager 析构体：Close()
  → sig_conn_ 成员释放强引用
  → event_loop_ 成员销毁，Quit 停止并等待信令调度线程
  → pullerWgt_ 成员销毁，再销毁其 AVPlayer
  → 基类 RtmpPushManager 析构，另一次 Close()
```

这里描述的是正常走到相应步骤时的顺序。`RemoteManager::Close()` 直接解引用 `sig_conn_` 判断 isPusher；若尚未 Init 或连接失败、该指针仍为空，这里会解引用空指针，不能保证继续完成后续析构。

还要注意两个依赖：被控端信令强引用先释放时，网络调度可能仍在运行；播放器却在信令 EventLoop 已销毁后才析构。不能把它画成“先完整停止所有业务对象，再退出循环”。

这些顺序不等于每次都会出错，但没有建立完整的回调与借用指针寿命约定。外层析构不能仅依靠成员声明顺序，必须先协调停止仍在访问成员的使用者。

### 7.2 Qt 对象销毁与普通回调要分开

| 情况 | 正确理解 |
| --- | --- |
| 关闭 PullerWgt 窗口 | 当前未接 closeEvent 到播放器 Close，也未设置 `WA_DeleteOnClose`；默认关闭后隐藏，不保证对象析构 |
| 断开 queued connection | 阻止后续通过该连接投递，已经排队的调用仍可能到达 |
| QObject 真正析构 | 自动断开相关 Qt signal 连接，并移除发给该对象的待投递事件 |
| 普通 std::function 捕获 this | 不受 Qt signal 自动断开规则管理，需先停止或撤销回调来源并等待在途调用 |
| `deleteLater()` | 安排延迟删除，需要相应事件循环能够处理；主事件循环停止后不能假定还会删除 |

Qt 规则见 [QWidget::close](https://doc.qt.io/qt-6/qwidget.html#close) 与 [QObject](https://doc.qt.io/qt-6/qobject.html)。queued 事件持有的 Frame 只保护媒体数据，不会替任意裸回调保护 AVPlayer。

`PullerWgt::player_` 同时是 unique_ptr 成员，且 AVPlayer 设置了 Qt parent。当前成员先析构删除子对象时，子对象会从 parent 的 children 中移除，不能仅凭这两种持有方式就判定必然重复 delete。仍需保证对象在合适线程、且工作线程和回调不再访问时销毁。参见 [Qt 对象树](https://doc.qt.io/qt-6/objecttrees.html)。

### 7.3 停线程之后，还要完成对应资源的释放

| 资源 | 正确配对或寿命要求 | 当前要读清的边界 |
| --- | --- | --- |
| 已打开的 FFmpeg 输入 | 停止读取并 join 后 `avformat_close_input` | 播放器输入上下文已放在读线程 join 后关闭，选项字典却提前释放 |
| codec context | 使用它的线程退出后 `avcodec_free_context` | 编码器管理器随后 reset；基类析构也参与释放，不能只读 Close 函数体就判断泄漏 |
| SwrContext | `swr_free` 才释放上下文 | `AudioResampler::Close` 只 swr_close 后置空，没有完成该释放 |
| Qt 音频输出 | 按对象归属与 API 约定停止输出，再销毁输出对象 | audioOut_ 无 parent，AudioRender 析构未删除它；device_ 是内部对象，不能单独 delete |
| OpenGL 纹理、缓冲区等 | 在有效且 current 的 context 下清理 | 当前纹理删除后 doneCurrent，再删除 VBO/EBO/VAO；program_ 也未见释放 |
| WASAPI COM 接口 | ComPtr 析构释放接口引用，必须晚于采集使用者结束 | 自动 Release 不会自动停止使用接口的线程 |
| [GetMixFormat](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getmixformat) 返回内存与 COM 初始化 | 对应 `CoTaskMemFree`；成功 COM 初始化按线程规则配对清理 | 未见格式内存释放；外层 Close 只 stop，未调用底层 exit |

WASAPI 的 COM 初始化与接口使用线程要求复用阶段六。[CoUninitialize](https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-couninitialize) 应配对到成功初始化的同一线程，不能随意放进任意析构回调；没有初始化成功也不能盲目配对。重采样器的关闭与释放参见 [libswresample](https://ffmpeg.org/doxygen/8.0/group__lswr.html)，OpenGL 清理条件参见 [QOpenGLWidget](https://doc.qt.io/qt-6/qopenglwidget.html#resource-initialization-and-cleanup)。

资源表的目的，是把“最后一个使用者结束”和“释放 API 实际执行”连起来。它不是要求本阶段一次修完所有资源问题。

## 8. 未开始、失败、重复停止与再次启动

### 8.1 用实际状态判断，不能只按正常成功路径推断

| 场景 | 当前事实 | 应得出的判断 |
| --- | --- | --- |
| 信令初始化未成功就销毁管理器 | `RemoteManager::Close` 未先判断 sig_conn_ | 析构也需要处理未初始化状态 |
| 播放尚未开始或已经 Close，再次 Close | AVPlayer 直接解引用 audioThread_/videoThread_ 后才检查 joinable | “有 joinable 判断”不代表线程指针本身安全 |
| 推流 Init 或 OpenUrl 中途失败 | 前面可能已启动底层采集，Open 返回 false，没有统一回滚 | 返回失败不代表没有后台线程和已分配资源 |
| 播放异步打开失败 | 读包线程返回，但外层已经创建两个输出线程，没有自动关闭它们 | 读线程结束不代表本次播放的所有线程均已结束 |
| 顺序重复停止与并发停止 | 推流 Close 有部分空指针保护，但没有统一并发保护 | 能连续调用两次，不等于两个线程可同时 Close |
| 停止后再次启动 | 推流 exit_ 未复位；播放 stop_ 未复位且 demux 已 reset | 不能仅再次调用 Open/HandleStartStream 就认定可重启 |
| 尚在运行时再次启动 | 可能替换对象与仍 joinable 的线程指针 | 启动也必须与正在运行、正在停止的状态协调 |

`AudioCapture/WASAPICapture` 析构体没有主动停止线程。部分初始化失败时，还需要追已创建的线程与回调，而不能只看最后一个“初始化完成”标志。

信令业务状态也有单独边界：当前 doDeleteStream 停止后没有将 PUSHER 恢复为 IDLE，而创建流分支又检查 IDLE。线程状态复位与业务状态复位缺一项，都可能影响再次开始。

### 8.2 先确定停止范围，再检查关闭顺序

停止一次推拉流时，只结束本次媒体工作并清理不再需要的会话资源；仍需处理后续信令或其他业务的连接和 EventLoop 应保留。销毁管理器或退出应用时，才需要结束它负责的全部业务，并最终停止对应的调度循环。

下面按依赖说明关闭所需的条件，不代表当前源码已经完整实现：

1. 确定本次停止的范围与协调者，阻止该范围内新的开始和提交。协调者不能等待自身退出。
2. 向相关媒体工作线程发出退出请求，让阻塞读取或等待有机会结束，再等待这些线程及对应回调结束。等待期间保留它们仍需访问的对象，也不持有退出所需的锁。
3. 确认没有使用者再访问某项资源后，处理相关剩余事件和数据，再按其要求清理。QObject 删除、OpenGL 清理和 COM 配对若需要特定线程或 context，必须在这些条件仍有效时完成，不能统一留到所有线程退出之后。
4. 对本次不再使用的连接，在调度器仍有效时完成注销与关闭协调；连接及回调目标要保留到相关回调不再执行或进入。只有结束某 EventLoop 负责的全部业务时，才停止并等待其调度线程，再完成相应对象的最终释放。
5. 进入本次操作对应的已停止状态。若要再次启动，重新建立所需对象与状态，不能只把一个 bool 改回 false。

本项目的 WASAPI 初始化由开始推流的信令回调调用。如果其中的 COM 初始化成功，配对清理就需要该信令线程仍能执行；不能先让它退出，再改由 GUI 线程补做。这也说明“使用者先停止”和“清理所需线程仍存活”必须同时满足。

主动停止可选择丢弃待播、待发尾部；正常 EOF 若要求完整播放，则要沿阶段八的排空关系继续处理。无论选择哪一种，都不能在仍有线程或回调使用资源时释放它。

## 9. 学习步骤：沿三条现有路径核对

### 第一步：先定入口和调用线程

从 doDeleteStream 跟到两个 HandleStopStream，再看析构与窗口关闭。对每个入口只回答：在哪个线程执行，会等待哪些线程，能否再次进入。

对照 `RemoteManager.h` 确认两条 EventLoop 分别由谁持有、哪些对象借用它们，不把信令循环和媒体循环混在一起。

### 第二步：跟一次推流停止

沿 `RtmpPushManager::Close → StopEncoder → StopCapture` 阅读，再进入 WASAPI/GDI 的停止。

对照第 4.1 节调用图指出三项：最后一次可能使用 Publisher 的位置、底层采集回调使用的缓冲区、每次 join 前已设置的退出条件。能说明当前提前释放 Publisher 的问题与采集回调的寿命即可，不要求先重写采编模块。

### 第三步：跟一次播放停止

沿 `AVPlayer::Close → AVDEMuxer 析构 → 两个解码器析构` 阅读，复用阶段八的四条队列。

指出输入中断依赖哪个对象存活、字典在哪释放、AVContext 与 queued Frame 还由谁持有。再对照音频对象和 OpenGL 清理，把工作线程结束与设备、context 清理分开。

### 第四步：回到连接和外层持有者

从 `RtmpPublisher::Close → TcpConnection::Close` 跟到 RmoveChannel，并对照派生类函数名；再看 EventLoop::Quit，确认工作线程何时不再进入回调。

最后读 RemoteManager 的实际析构顺序，用“还有谁可能访问它”检查每个被释放对象。已有运行条件时，可复用一次正常停止和一个实际遇到的未连接、取消或读流结束场景，用断点或已有日志观察线程退出与析构；没有条件时，按源码推演即可。

不必为本阶段搭建新服务、制造全部失败分支或编写完整退出测试框架。真实双端启动与停止复用 ENET [阶段十二统一联调](https://github.com/slimesq/ENET/blob/main/docs/项目学习规划.md#stage-12)，已得到的观察结果直接复用。
