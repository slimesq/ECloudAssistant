# ECloudAssistant 阶段零：工程与构建基线学习讲义

> 对应[项目学习规划的阶段零](项目学习规划.md#stage-0)。参考用时：3～5 小时，工具与依赖安装、环境排障另计。
>
> 本阶段先在 Windows 上构建主程序，认清依赖、源码范围和真实入口，再观察启动与退出。已有 C++ 和 ENET 构建经验直接复用；Qt、Winsock、采集编码和渲染的内部原理在后续阶段补学。

## 1. 学完后应能回答什么

1. 哪些源码进入 `ECloudAssistant`，哪些演示文件被排除？
2. 配置、编译、链接和运行各依赖什么，错误发生在哪一层？
3. 本次实际使用哪个 Qt Kit、FFmpeg 开发包，程序和调试产物在哪里？
4. 主窗口显示前已经做了什么，退出时哪些条件尚需核对？

本讲命令在 **Windows 端、已初始化 MSVC x64 环境的 PowerShell 中、客户端仓库根目录**执行。仓库的实际磁盘位置不影响步骤。

可以先完成构建与入口阅读，再进入客户端阶段二。阶段一只在出现对象、回调或线程疑问时按需查阅。

## 2. 先认清主目标与源码范围

### 2.1 一个 GUI 程序，多组源码

[顶层 CMakeLists.txt](../CMakeLists.txt) 声明一个主可执行目标：

```cmake
add_executable(ECloudAssistant WIN32 ${PROJECT_SOURCES})
```

`WIN32` 在这里表示 Windows GUI 程序，不表示强制编译为 32 位；x64 取决于实际工具链。程序也不会因此自动带一个控制台窗口，见 [CMake add_executable](https://cmake.org/cmake/help/latest/command/add_executable.html)。

| 源码位置 | 在主程序中的职责 | 后续阅读阶段 |
| --- | --- | --- |
| [main.cpp](../main.cpp)、[ECloudAssistant.cpp](../ECloudAssistant.cpp) | 应用入口、主窗口与区域组合 | 2 |
| `UI/` | 页面、登录与远程操作入口、样式资源 | 2～3、5 |
| `Net/` | Winsock、select 调度、缓冲、信令和输入执行 | 4～5、9 |
| `Codec/` | FFmpeg 编解码、解封装、转换和媒体队列 | 6、8～9 |
| `Pusher/` | 采集与编码组织、RTMP 发布 | 6～7 |
| `Puller/` | 播放窗口、图像和声音输出、输入产生 | 5、8～9 |
| [res.qrc](../res.qrc) | 将样式、图片和着色器等资源纳入程序 | 本阶段只定位资源文件，使用原理随对应阶段学习 |

这些目录的源码直接进入同一个目标，不是每个目录生成一个独立程序。编译时看到媒体和 Windows API 文件，并不要求现在就读懂它们的全部业务。

### 2.2 文件在仓库中，不等于进入主构建

CMake 收集仓库根目录，以及 `UI/`、`Net/`、`Codec/`、`Pusher/`、`Puller/` 下的 `.cpp/.h`，再明确排除：

```text
Net/main.cpp
Net/Acceptor.cpp
Net/Acceptor.h
Net/EpoolTaskScheduler.cpp
Net/EpoolTaskScheduler.h
Net/TcpServer.cpp
Net/TcpServer.h
```

因此，客户端主入口是根目录 `main.cpp`，不是 `Net/main.cpp`；网络主线使用 `SelectTaskScheduler`，不要因仓库中存在 epoll 文件，就沿那份演示分析主程序。

### 2.3 自动生成文件与资源文件是什么

目标开启了：

- `AUTOMOC`：为带有 `Q_OBJECT` 等声明的类运行 Qt 元对象编译器 moc，生成信号等机制所需的 C++ 代码。
- `AUTORCC`：把 `res.qrc` 中列出的资源交给 rcc 处理，生成可链接的资源代码。

当前界面主要由 C++ 创建控件和布局，未开启 `AUTOUIC`。不要把自动生成的 moc、qrc 文件当作新的业务入口，也不需要手工修改它们。

`:/UI/brown/main.css` 等路径来自 Qt 资源系统，不是仓库在本机的绝对位置。样式、图片和着色器资源与运行时 DLL、Qt 插件的查找是不同层次的问题。

## 3. 区分构建依赖与运行依赖

### 3.1 先复用熟悉的构建概念

| 环节 | 本项目做什么 | 观察位置 |
| --- | --- | --- |
| 配置与生成 | 检查 Windows 平台、工具链、Qt、FFmpeg，生成 Ninja 规则 | CMake 输出、`CMakeCache.txt` |
| 编译 | 编译业务源码，以及生成的 moc/qrc 源码 | 编译器诊断、`.obj` |
| 链接 | 将目标文件和依赖库组成 `ECloudAssistant.exe` | 链接命令、未解析符号等诊断 |
| 运行 | Windows 加载 EXE、DLL 和插件，执行入口及业务 | 调试器、加载错误、日志和进程行为 |

本项目中，CMake 读取构建描述并生成规则；Ninja 按规则调用 MSVC 的编译器 `cl` 和链接器 `link`。`cmake --build` 是调用构建工具的统一入口，此处实际驱动的是 Ninja。

构建需要 Qt、FFmpeg 的开发文件，但不需要先启动 ENET 服务。服务端不可达属于运行业务条件，不能用它解释找不到头文件或链接符号。

### 3.2 当前目标链接哪些依赖

| 依赖 | CMake 中的组件 |
| --- | --- |
| Qt | Core、Gui、Widgets、Network、Multimedia、OpenGL；Qt 6 额外要求 OpenGLWidgets |
| FFmpeg | avcodec、avdevice、avformat、avutil、swresample、swscale |
| Windows 系统库 | ws2_32、gdi32、user32、ole32、ksuser |

现阶段只知道这些组件分别支撑界面、网络、媒体和系统调用即可。Windows 头文件与系统库来自工具链和 Windows SDK；具体 API 放到客户端阶段四至六学习。

FFmpeg 开发包至少要区分：

| 内容 | 用在哪一步 |
| --- | --- |
| `include/libavcodec/avcodec.h` 等头文件 | 编译时提供声明 |
| 可供 MSVC 链接的导入库，如 `avcodec.lib` | 链接时解析 DLL 提供的符号 |
| 配套的运行时 DLL | 程序启动或使用对应组件时加载 |

导入库供链接器建立对 DLL 的引用，不会把 DLL 的完整实现复制进 EXE，因此链接成功后仍需要对应 DLL。Windows 的 `.lib` 也可能是静态库，不能仅凭扩展名判断。

仅有可运行的 `ffmpeg.exe`，不代表开发依赖已经齐全；也不能把 Linux 库或任意 MinGW 库直接当作 MSVC 的配套依赖。

### 3.3 选择匹配的工具链与依赖

使用与 MSVC 工具链兼容的 **Qt Windows x64 Kit**。Kit 可以理解为一套配套的 Qt 头文件、库、工具及其编译器配置，不能把 MinGW Kit 与本例 MSVC 路线混用。

CMake 能查找 Qt 6 或 Qt 5，源码也存在两版的条件分支；这不等于所有 Qt 版本都已验证。FFmpeg 代码使用 `ch_layout`、`AVChannelLayout` 等接口，也不能随意换成不具备这些接口的旧开发包。

优先复用已有能够匹配的组合。FFmpeg 的头文件、导入库与 DLL 应来自相容的同一套 x64 开发包；Qt 的 Debug/Release 库与插件要匹配本次构建。FFmpeg SDK 不一定提供带 `d` 后缀的 Debug DLL，不能照搬 Qt 的命名规则判断它。

`third_party/` 已被 [.gitignore](../.gitignore) 排除，新机器 clone 后不一定有依赖。仓库当前没有现成的依赖下载或 DLL 部署脚本，不能把目录存在当作已经具备自动准备能力。

### 3.4 Qt 与 FFmpeg 怎样被 CMake 找到

| 定位入口 | 当前实现的含义 |
| --- | --- |
| `-DCMAKE_PREFIX_PATH=...` | 显式给出 Qt 等包的查找前缀，本讲指向选定 Qt Kit 根目录 |
| 环境变量 `QTDIR` | 仅在 `CMAKE_PREFIX_PATH` 为空时，由本项目追加到查找前缀 |
| `-DFFMPEG_ROOT=...` | 本项目的 CMake cache 参数，从该根目录查找 `include` 和 `lib` |
| 环境变量 `FFMPEG_HOME` | FFmpeg 根目录提示 |
| 环境变量 `FFMPEG_INCLUDE/FFMPEG_LIB` | 分别提示头文件与库目录 |

`FFMPEG_ROOT` 是 CMake 参数，当前代码没有读取环境变量 `$env:FFMPEG_ROOT`。仅设置这个同名环境变量，并不保证配置时会使用它。

`-D名称=值` 会设置或更新当前构建目录中的 CMake 缓存项。`CMakeCache.txt` 保存构建选项和已经找到的依赖路径，后续配置通常会复用；它与 PowerShell 环境变量是两种不同的设置方式，见 [CMake 命令行说明](https://cmake.org/cmake/help/v3.25/manual/cmake.1.html)。

这些路径用于定位开发依赖，不会自动完成运行时 DLL 部署。

## 4. 预设与 MSVC 开发环境

### 4.1 两个预设各保存了什么

对照 [CMakePresets.json](../CMakePresets.json)：

| 预设 | 生成器 | 构建类型 | 构建目录 |
| --- | --- | --- | --- |
| `msvc-debug` | Ninja | Debug | `build/ninja-debug/` |
| `msvc-release` | Ninja | Release | `build/ninja-release/` |

主线使用 Debug。Ninja 在这里是单配置生成器，Debug 来自配置时的 `CMAKE_BUILD_TYPE`，不是构建时随意切换的选项。

文件中有两类预设：`configurePresets` 保存配置与生成选项；`buildPresets` 通过 `configurePreset` 指向相应配置。两类都用了 `msvc-debug` 这个名字，但 `cmake --preset msvc-debug` 只配置和生成，`cmake --build --preset msvc-debug` 才执行构建。

顶层要求 CMake 3.25，预设使用 schema 6，也需要 CMake 3.25 及以上，见 [CMake 预设版本说明](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html#versions)。

### 4.2 预设的 x64 字段不负责替终端初始化环境

预设中的 `architecture` 与 `toolset` 使用 `strategy: external`。CMake 命令行不会据此自动准备 MSVC；IDE 可以利用这些字段初始化环境，见 [CMake external 策略](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html#configure-preset)。

使用已经初始化 x64 工具链的 Visual Studio 开发终端。若打开的是 **x64 Native Tools Command Prompt**，先在其中运行 `powershell`，让新 PowerShell 继承该环境，再进入客户端仓库根目录执行下文。环境准备方式见 [Microsoft 命令行构建说明](https://learn.microsoft.com/en-us/cpp/build/building-on-the-command-line?view=msvc-170)。

先确认：

```powershell
Get-Command cl, cmake, ninja
cmake --version
cmake --list-presets
```

应能找到 MSVC、CMake 与 Ninja，并列出 `msvc-debug/msvc-release`。普通 PowerShell 中即使能找到 CMake，也不代表已有 MSVC 的头文件、链接库和架构环境。

若缺少 MSVC 或 Windows SDK，先在 Visual Studio Installer 中检查“使用 C++ 的桌面开发”工作负载；若缺少 CMake 或 Ninja，再补齐相应工具。打开开发终端只会初始化已有工具的环境，不会自动安装它们。

## 5. 完成 Debug 构建并核对产物

### 5.1 配置并构建

已有正确依赖定位时，直接执行：

```powershell
cmake --preset msvc-debug
cmake --build --preset msvc-debug
```

只在依赖未定位时，再明确指定。将下面的 Qt 占位路径替换为选定的 MSVC x64 Kit 根目录；FFmpeg 示例沿用仓库下已准备好的开发包，放在其他位置时替换对应赋值。

Qt Kit 根目录应包含 `bin/`、`include/`、`lib/`；下例假定 FFmpeg SDK 也按 `include/`、`lib/`、`bin/` 组织。传入根目录，不要传入其 `bin/` 子目录或 Qt 安装总目录。若本地还没有 FFmpeg SDK，应先准备第 3 节所述开发包，下面的 `Resolve-Path` 只解析已有目录，不会下载依赖。

```powershell
$qtKit = "<Qt MSVC x64 Kit 根目录>"
$ffmpegSdk = (Resolve-Path ".\third_party\ffmpeg").Path
cmake --preset msvc-debug "-DCMAKE_PREFIX_PATH=$qtKit" "-DFFMPEG_ROOT=$ffmpegSdk"
cmake --build --preset msvc-debug
```

`$qtKit` 和 `$ffmpegSdk` 是当前 PowerShell 的普通变量，供命令传参，不是设置全局环境。

配置成功后再构建。遇到错误时，先看第一处实际诊断属于哪个环节，不必为本阶段逐行读完报错模块的业务。

### 5.2 核对本次配置与构建产物

```powershell
Get-Item ".\build\ninja-debug\bin\ECloudAssistant.exe"
Select-String -Path ".\build\ninja-debug\CMakeCache.txt" -Pattern "CMAKE_BUILD_TYPE:|CMAKE_CXX_COMPILER:|QT_DIR:|Qt5_DIR:|Qt6_DIR:|FFMPEG_INCLUDE_DIR:|FFMPEG_.*_LIBRARY:"
```

| 产物 | 用途 |
| --- | --- |
| `build/ninja-debug/bin/ECloudAssistant.exe` | 主程序 |
| 构建目录中的 PDB | Debug 调试信息，具体位置看本次产物 |
| `build/ninja-debug/compile_commands.json` | 本次编译命令与头文件搜索参数 |
| `ECloudAssistant_autogen` 下的生成文件 | moc、qrc 等构建生成内容 |
| `CMakeCache.txt`、`build.ninja` | 配置结果与构建规则 |

已有 EXE、旧日志或历史 cache 只能提供线索，不能替代当前构建是否成功的判断。本阶段应能把本次构建输出与当前工具链、依赖和产物对应起来。

### 5.3 切换依赖时检查缓存（按需）

切换 Qt Kit、FFmpeg 开发包或目标架构后，先检查 cache 是否仍指向旧依赖；仅修改 PATH 或根目录提示，不一定重做已有的查找结果。

确需重置本预设配置时，可使用 CMake 的 `--fresh` 重新配置，再构建。以下命令使用第 5.1 节的 `$qtKit` 和 `$ffmpegSdk`；若之前直接复用已有配置，请先按本次依赖选择为这两个变量赋值：

```powershell
cmake --fresh --preset msvc-debug "-DCMAKE_PREFIX_PATH=$qtKit" "-DFFMPEG_ROOT=$ffmpegSdk"
cmake --build --preset msvc-debug
```

`--fresh` 会移除该构建目录的 `CMakeCache.txt` 和 `CMakeFiles/` 并重新配置，详见 [CMake --fresh](https://cmake.org/cmake/help/v3.25/manual/cmake.1.html#cmdoption-cmake-fresh)。它不负责清理整个输出目录或重新准备运行 DLL。这是切换依赖或配置失配时的处理方式，不是每次构建的固定步骤。

### 5.4 处理编辑器解析问题（按需）

[.vscode/settings.json](../.vscode/settings.json) 让 clangd 从工作区根目录读取 `compile_commands.json`，并配置 CMake Tools 复制编译数据库。单独在终端构建时，不会自动执行编辑器的这项复制。

需要更新根目录编译数据库时：

```powershell
Copy-Item ".\build\ninja-debug\compile_commands.json" ".\compile_commands.json"
```

优先以本次实际编译结果判断构建问题，再用正确的编译数据库解决编辑器解析。当前 [.vscode/tasks.json](../.vscode/tasks.json) 只提供 Debug 构建任务，没有预置的 `launch.json`；调试时使用现有 IDE 或调试器选择本次目标，在 `main` 设置断点。

## 6. 首次运行前准备 DLL 与 Qt 插件

### 6.1 构建成功还不等于运行依赖齐全

CMake 的依赖查找路径不会自动成为 Windows 运行时的 DLL 搜索路径。将匹配的普通依赖 DLL 放到 EXE 所在目录，是利用 Windows 默认搜索位置准备本机运行环境，见 [Microsoft DLL 搜索顺序](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order)。

当前 CMake 没有自动执行 `windeployqt` 或复制 FFmpeg DLL。启动程序前，至少要保证：

- 本次 Qt Kit 对应的运行库和平台插件可被找到。
- 链接的 FFmpeg 开发包对应 DLL 及其间接依赖可被找到。
- 架构和本次构建配置匹配。

例如，Qt Debug 程序通常使用带 `d` 后缀的 Qt DLL 和 `platforms/qwindowsd.dll`。不要从另一个 Qt Kit 随意混入同名插件。

平台插件本身也是 DLL，用于衔接 Qt 与 Windows 窗口系统；Qt 在运行时按插件路径加载它。使用下面的部署工具时，应保留生成的 `platforms/` 等子目录结构，不能把插件 DLL 全部移到 EXE 同级目录，见 [Qt Windows 平台插件说明](https://doc.qt.io/qt-6/windows-deployment.html#qt-plugins)。

Qt 的样式资源已经编入程序，不代表 `platforms` 插件或 FFmpeg DLL 也已包含在 EXE 中。

### 6.2 使用同一 Qt Kit 的部署工具

如果当前输出目录尚未准备运行依赖，确认 `$qtKit` 与 `$ffmpegSdk` 对应本次 cache 实际选中的依赖，再执行：

```powershell
& "$qtKit\bin\windeployqt.exe" --debug ".\build\ninja-debug\bin\ECloudAssistant.exe"
Get-ChildItem -LiteralPath (Join-Path $ffmpegSdk "bin") -Filter "*.dll" -File | Copy-Item -Destination ".\build\ninja-debug\bin"
```

第一条使用选定 Kit 的 `windeployqt` 准备所需 Qt 运行库与插件；第二条复制同一 FFmpeg SDK 的 DLL。若前面沿用了已有配置，应先依据 cache 填好这两个变量，不能拿未赋值或其他版本的变量直接使用。

例如，cache 中的 `Qt5_DIR` 或 `Qt6_DIR` 通常指向 Kit 下的 `lib/cmake/Qt5` 或 `lib/cmake/Qt6`，不是 `$qtKit` 要填写的根目录。命令开头的 `&` 是 PowerShell 调用运算符，用来执行引号内的程序路径。

`windeployqt` 不负责所有第三方库，FFmpeg 仍需单独准备。工具说明按实际 Qt 主版本查阅：[Qt 5 部署文档](https://doc.qt.io/archives/qt-5.15/windows-deployment.html)、[Qt 6 部署文档](https://doc.qt.io/qt-6/windows-deployment.html)。

需要查看 EXE 直接导入的 DLL 名称时，可在同一开发环境运行：

```powershell
dumpbin /dependents ".\build\ninja-debug\bin\ECloudAssistant.exe"
```

这能帮助核对依赖名称，不证明所有文件或动态加载的插件都已找到。首次学习只准备当前机器的运行条件，发布安装包不属于本阶段。

## 7. 从真实入口看首次启动

### 7.1 从 main 到主窗口

```text
main
  → 创建 QApplication
  → 创建 ECloudAssistant
      → MainWgt
          → LoginWgt
          → RemoteWgt → RemoteManager
          → 设备页、设置页占位 QWidget
          → 默认显示 remoteWgt
      → TitleWgt、ListInfoWgt
  → w.show()
  → QApplication::exec()
```

[main.cpp](../main.cpp) 中的独立播放器和推流测试已经注释。主线是创建窗口后进入 Qt 事件循环，本阶段先认清调用边界，Qt 对象、页面和 signal/slot 在阶段二展开。

### 7.2 默认页面与联网时机不是一回事

[LoginWgt](../UI/center/LoginWgt.cpp) 构造时已尝试连接固定的负载地址 `192.168.31.30:8523`，并在 GUI 线程调用 `waitForConnected(1000)`。连接成功会立即发送入口查询。

因此：

- 窗口显示前就可能等待这次连接。
- 默认显示远程页，不代表登录页没有创建或没有联网。
- 主窗口能够显示，不代表负载、登录、信令或媒体链路已经成功。

当前阶段只定位这次自动操作。地址切换与报文处理在阶段三学习，完整两端联调仍按总体规划安排。

### 7.3 构造窗口时已经有自建调度线程

[RemoteManager](../UI/center/RemoteManager.h) 继承 `RtmpPushManager`，按构造顺序看：

```text
RtmpPushManager 基类构造 → EventLoop(1)
RemoteManager 自身构造  → EventLoop(2)
EventLoop 构造          → Loop → SelectTaskScheduler 工作线程
```

所以这里已创建两组调度器，共 1+2 个自建调度工作线程。`EventLoop(n)` 的参数在本实现中决定创建多少个调度器及其工作线程；1+2 也不是整个进程的线程总数。

`QApplication::exec()` 在主线程运行 Qt 事件循环，处理界面事件等；[Net/EventLoop](../Net/EventLoop.cpp) 创建的是另外的网络调度工作线程。两者分工不同，线程与回调关系在阶段四展开。

屏幕与音频采集线程在 [RtmpPushManager::Open()](../Pusher/RtmpPushManager.cpp) 调用 `Init()` 的过程中启动；`Init()` 返回 true 且 `OpenUrl()` 返回 0 后，才创建 `EncodeVideo/EncodeAudio` 工作线程。它们都不在窗口构造阶段启动。这里 `OpenUrl()` 返回 0 只表示已建立 TCP 连接并发起 RTMP 握手，没有等待服务端确认发布成功。采集与编码在阶段六展开，发布状态在阶段七展开。

### 7.4 观察启动与退出

运行条件准备好后，可以直接启动本次产物，观察默认页面和退出：

```powershell
& ".\build\ninja-debug\bin\ECloudAssistant.exe"
```

需要观察窗口构造顺序时，再用已有调试器在 `main` 设置断点。本阶段不要求点击开始远控、启动采集或拉流。

与本次退出直接相关的是 [RemoteManager 的析构与 Close()](../UI/center/RemoteManager.cpp)：析构函数调用 `Close()`，后者未判空就访问 `sig_conn_`。未初始化信令或连接失败时，该指针可能为空，关闭窗口时就可能在这里出错。

构建成功、窗口显示和正常退出需要分别确认。若退出卡住或崩溃，先根据调用栈定位；已理解的小问题可按阶段一处理。播放器线程与完整关闭关系在阶段九检查，完成阶段零不要求启动媒体链路或修完全部关闭问题。

## 8. 遇到问题先定位在哪一层

| 现象 | 优先核对 |
| --- | --- |
| 提示只支持 Windows | 是否误在 WSL/Linux 中配置客户端 |
| 找不到 `cl`、Windows SDK 头文件或库 | MSVC x64 开发环境是否已初始化 |
| 找不到 Ninja | 开发环境中 Ninja 是否可用，是否误只准备了 CMake |
| 找不到 Qt 包或组件 | Kit 根目录、组件是否齐全、cache 实际选择 |
| 找不到 FFmpeg 头文件或链接库 | 开发包是否包含 include 与 MSVC 可用的导入库，定位参数是否正确 |
| 结构体成员或 API 不存在 | 依赖版本与当前源码接口，先看首个编译诊断 |
| 链接有未解析符号、架构冲突 | 本次库版本、架构及链接命令 |
| 启动提示缺 DLL、入口点或 Qt 平台插件 | 同套运行库、插件目录、Debug/Release 与架构 |
| 程序出现后业务无响应 | 先区分服务不可达、源码状态分支和媒体条件 |
| 未连服务时退出异常 | `RemoteManager::Close` 等实际调用栈，不直接归因于 Qt 或 FFmpeg 安装 |

只有构建环境本身仍不清楚时，才复用一个现成 Qt 官方示例确认工具链；不要求另建一套示例工程。当前无法运行时，仍可先完成主目标、依赖和入口的源码阅读，运行结果保留待验证。
