## 2. 读源码前，先补这三组知识

### 2.1 容器、流、Packet 与 Frame

先把“输入里装着什么”和“解码后得到什么”分开。容器（封装格式）组织编码数据及其时间等信息，例如 MP4、FLV；网络协议负责传输。FFmpeg 用 `AVFormatContext` 管理一次媒体输入，再由解封装器读出各路编码数据。

| 名称 | 含义 | 本阶段观察的字段 |
| --- | --- | --- |
| `AVFormatContext` | 一次媒体输入的上下文，保存流信息并参与解封装读取 | `streams/nb_streams` |
| `AVStream` | 输入中的一路媒体轨道，视频和音频通常是不同的流 | `codecpar`、`time_base`、流索引 |
| `AVPacket` | 解封装后的一份编码数据及时间等信息 | `data/size`、`stream_index`、`pts/dts` |
| `AVFrame` | 解码后的图像或音频采样，也可表示转换后的原始数据 | 视频的 `width/height/format/data/linesize`；音频的 `sample_rate/ch_layout/format/nb_samples` |

这里的 Packet 既不是 TCP 包，也不是 RTMP Chunk。`av_read_frame` 名字中的 frame 也不代表它返回了 `AVFrame`，它输出的是 `AVPacket`。

解码可能有缓存与重排序。一份 Packet 被接受后，暂时没有 Frame、得到一个 Frame，或者需要多次 receive 才取完输出，都不能简单按“一包必出一帧”理解。音频 Frame 中的 `nb_samples` 是**每声道的采样数**，不是字节数。

先读匹配本地 FFmpeg 版本的 [demux_decode.c](https://ffmpeg.org/doxygen/8.0/demux_decode_8c-example.html) 中“打开输入、按 stream_index 分流、送包、循环取帧”几段即可。这个示例把原始数据写到文件，不提供 Qt 画面和声音播放；不要把“解码成功”当作“播放器已完成输出”。

### 2.2 解码 send/receive：输入被接受，不等于已有输出

与阶段六编码方向相反：

`AVPacket → avcodec_send_packet → 解码器 → avcodec_receive_frame → AVFrame`

按下面的状态关系理解 API，再与项目对照：

| 操作或返回值 | 含义与后续动作 |
| --- | --- |
| `send_packet` 返回 0 | 本次输入已被接受，接着尝试取输出 |
| `receive_frame` 返回 0 | 得到一个有效 Frame；处理后继续 receive |
| receive 返回 `AVERROR(EAGAIN)` | 当前输出取完，需要更多输入 |
| send 返回 `AVERROR(EAGAIN)` | 当前输入未被接受；先取已有输出，再重试这份输入 |
| receive 返回 `AVERROR_EOF` | 解码器排空，后续没有输出 |
| 其他负数 | 错误，应停止使用本次无效结果并处理失败 |

正常输入结束后，向解码器提交空 Packet，继续 receive 到 EOF，才能取出内部延迟输出。这里的“空 Packet”指 API 的结束输入操作，通常传 `nullptr`，不是把一个正常 Packet 的 `size` 随意改为 0。

FFmpeg 的 [send/receive 文档](https://ffmpeg.org/doxygen/8.0/group__lavc__encdec.html)是返回值与排空行为的依据。

### 2.3 OpenGL 与 PCM 输出：先认识最小组成

你没有渲染基础，先按“把一张图贴到矩形上”理解本项目：

| 概念 | 在本项目中的作用 |
| --- | --- |
| OpenGL context | 保存 OpenGL 状态及资源关系；调用相关 API 时，需将它设为当前线程的当前上下文（current） |
| 纹理 | 保存上传到 GPU 的图像；这里 Y、U、V 各用一张 |
| 纹理坐标 | 指出矩形上的位置应从图像的哪里采样 |
| VBO / EBO / VAO | 分别保存顶点数据、索引和顶点布局等状态 |
| 顶点着色器 | 处理顶点位置，把纹理坐标传给后续阶段 |
| 片段着色器 | 对矩形覆盖的像素采样 YUV，计算要输出的 RGB |
| viewport（视口） | 绘制目标中的矩形区域，将顶点坐标映射到这个区域；本项目用它居中显示画面 |
| `initializeGL/resizeGL/paintGL` | 初始化资源、调整显示区域、执行绘制 |
| `update()` | 请求后续重绘，调用时并不立即完成一次绘制 |

`QOpenGLWidget::makeCurrent()` 使本控件的 context 成为当前线程使用的 context；`doneCurrent()` 解除当前绑定，并不是销毁 context。

当前只有四个顶点、六个索引，组成两个三角形覆盖一个矩形。每个顶点包含三个位置分量与两个纹理坐标分量；不需要先学习三维相机、光照和模型加载。

对照 Qt [Hello GL2](https://doc.qt.io/qt-6/qtopengl-hellogl2-example.html) 找到三个回调、顶点设置与绘制调用即可，不要求先读懂它的全部三维造型。`QOpenGLWidget` 对 context 和回调的约定见[官方文档](https://doc.qt.io/qt-6/qopenglwidget.html)。

声音输出则先认识四项：

1. `QAudioFormat` 描述采样率、声道与样本格式，必须与送入的 PCM 一致。
2. Qt 6 的 `QAudioSink` 接收原始音频；本项目 Qt 5 分支使用旧版 `QAudioOutput`。
3. 无参数 `start()` 返回可写的 `QIODevice`；向它写 PCM，由输出设备按采样率消耗。
4. 空闲字节数表示缓冲区还可接收多少数据，`write()` 返回本次实际接受的字节数；它们都不等于已经从扬声器播放完毕。

可先读匹配 Kit 的 [Audio Output Example](https://doc.qt.io/qt-6/qtmultimedia-audiooutput-example.html) 中格式设置、启动、供数与停止。Qt 6 同名 `QAudioOutput` 用于另一套媒体播放接口，读项目时不要与 Qt 5 的 PCM 输出类混用。有现成示例可直接运行观察；没有运行条件时，先按这些对象与调用读代码。

## 3. 从开始拉流到读包分流

### 3.1 “开始”是异步发起

构造播放页面时，在 GUI 路径完成：

`PullerWgt → AVPlayer 构造 → Init → 创建 AVContext/AVDEMuxer → InitAudio(2, 44100, 16) → 连接 sig_repaint`

阶段五已经跟过信令的开始回调。当前回调直接调用 `HandleStartStream(streamAddr)`，执行位置在信令调度线程，不能因为它是 QWidget 成员函数就认定在 GUI 线程运行。

开始路径为：

```text
HandleStartStream
  → AVDEMuxer::Open
      → 创建读包 std::thread，执行 FetchStream
      → 立即返回 true
  → 创建 audioPlay 输出线程
  → 创建 videoPlay 输出线程
  → 返回 true

读包线程：
  FetchStream
    → FetchStreamInfo
        → avformat_open_input
        → avformat_find_stream_info
        → 选择流，打开相应解码器并启动其 QThread
    → 循环 av_read_frame
```

输出线程可能在流信息读取和解码器初始化完成前就启动；队列为空时，它们轮询等待数据。

`Open()` 的 true 只表示已发起读线程，不证明地址可用、解码器已经打开或媒体已经播放。`streamCb_` 默认是可调用的空操作，当前 `AVPlayer` 未设置处理打开结果的回调。`HandleStartStream()` 不等待这个结果，而是在创建音视频输出线程后返回 true；读线程的打开失败没有通过这条返回值传给调用方。

### 3.2 流索引怎样决定去向

`FetchStreamInfo()` 遍历 `streams`，按 `codec_type` 记录索引。存在多路同类流时，当前保留遍历到的最后一路视频或音频，并未调用“自动选择最佳流”的逻辑。

两个解码类虽然叫 `H264_Decoder/AAC_Decoder`，实际通过 `codecpar->codec_id` 查找解码器。类名不能代替输入的真实编码信息；后续转换与输出仍有自己的格式假设。

`codecpar` 还携带该流的尺寸、采样参数与 `extradata` 等解码配置。两个解码器的 `Open()` 先创建 codec context，再用 `avcodec_parameters_to_context()` 复制参数，最后调用 `avcodec_open2()`。由 FFmpeg 取得的编码配置通过这条路径参与解码初始化，与阶段七发布的配置数据接上。

随后每次新建 Packet，再调用 `av_read_frame`：

| `packet->stream_index` | 当前处理 |
| --- | --- |
| 等于视频索引 | 放入 `H264_Decoder` 内部的 Packet 队列 |
| 等于音频索引 | 放入 `AAC_Decoder` 内部的 Packet 队列 |
| 其他流 | unref，不参与本播放器输出 |

`duration × time_base` 得到的是时长信息，不是播放调度器；直播时长还可能未知。字典中的 `nobuffer/low_delay` 等选项，也不能仅凭名称证明当前链路没有缓存或延迟。

### 3.3 按执行位置读，避免把对象与线程混为一谈

| 执行位置 | 主要工作 |
| --- | --- |
| GUI 线程 | 创建播放控件和 Qt 音频对象，处理 queued 视频槽与绘制回调 |
| 信令调度线程 | 接收开始/停止指令，直接调用对应播放成员函数 |
| 读包 std::thread | 打开媒体、读流信息、读取并分发 Packet |
| 两个解码 QThread 的 `run()` | 分别消费 Packet，解码并转换，产生 Frame |
| `videoPlay` std::thread | 消费视频 Frame，发送 queued 信号 |
| `audioPlay` std::thread | 消费音频 Frame，调用音频写入 |

这是项目可见的工作划分，FFmpeg 和音频后端还可能使用内部线程。QThread 对象本身的归属线程与 `run()` 的执行线程也要区分；不能把对该对象的所有普通成员调用都视作自动进入 `run()`。

## 4. Packet 怎样经过解码，进入 Frame 队列

### 4.1 先把四条队列分清

```text
av_read_frame
  ├─ 视频 Packet 队列（H264_Decoder）
  │    → 视频解码线程 → 接收图像 → VideoConverter → YUV420P
  │    → 视频 Frame 队列（AVContext）
  │    → videoPlay → queued sig_repaint → GUI
  │
  └─ 音频 Packet 队列（AAC_Decoder）
       → 音频解码线程 → 接收采样 → AudioResampler → 44100Hz/双声道/S16
       → 音频 Frame 队列（AVContext）
       → audioPlay → AudioRender::Write → Qt 音频设备
```

| 队列所在对象与成员 | 元素类型 | 生产者 → 消费者 |
| --- | --- | --- |
| `H264_Decoder::video_queue_` | `AVPacketPtr` | 读包线程 → 视频解码线程 |
| `AAC_Decoder::audio_queue_` | `AVPacketPtr` | 读包线程 → 音频解码线程 |
| `AVContext::video_queue_` | `AVFramePtr` | 视频解码线程 → videoPlay |
| `AVContext::audio_queue_` | `AVFramePtr` | 音频解码线程 → audioPlay |

同名的 `video_queue_/audio_queue_` 不代表同一个队列。先看它属于哪个对象，再看模板参数。

两级队列将读包、解码和输出分开，使某一层暂时较慢时不必立即卡住所有处理。但队列也保存数据、占用内存，是否限制积压要继续查实现。

### 4.2 两个解码线程实际做什么

每路基本过程是：

1. 等自己的 Packet 队列有数据，出队一个 Packet。
2. 调用 `avcodec_send_packet`。
3. 循环 `avcodec_receive_frame`，遇到 EAGAIN 或 EOF 结束这轮取帧。
4. 对每次有效解码结果做格式转换，将转换结果放进 `AVContext` 的 Frame 队列。

两路都循环 receive，并非 send 一次只取一次输出。当前代码与第 2.2 节的完整状态处理仍有差距：

- send 的任何非零结果都会终止解码循环，未对 EAGAIN 做“取输出后重试原 Packet”。
- 音频 receive 遇其他负数直接退出；视频只特别检查 EAGAIN/EOF，其他错误还可能继续进入转换。
- 两路都把 `Convert()` 的整数结果直接当 bool。正数表示产生有效输出，0 表示暂无输出，负数表示错误；负数也会被当作 true。后面的非空指针检查不能代替转换成功检查。

因此阅读时先确认返回值有效，再解释后续数据，不能把当前所有入队路径都描述为已经正确过滤错误。

### 4.3 转换解决“能解码”与“能输出”的差异

| 分支 | 解码输出可能是什么 | 项目转换结果 | 对应输出端 |
| --- | --- | --- | --- |
| 视频 | 解码器决定的像素格式与尺寸 | `VideoConverter` 转为 YUV420P | 三张单通道纹理 |
| 音频 | 输入决定的采样率、声道、packed/planar 格式 | `AudioResampler` 转为 44100Hz、双声道、S16 packed | `InitAudio(2, 44100, 16)` |

视频调用 `sws_scale`，按输入和输出的 `data/linesize` 处理各行。转换器在 Open 时按 codec context 的尺寸和格式建立，当前没有随实际解码 Frame 的变化重新配置；不能把渲染端能重建纹理等同于整条链路支持动态格式变化。

音频调用 `swr_convert`。输出缓冲容量按重采样器延迟与输入采样数估算，转换后再用返回的有效采样数更新输出 Frame 的 `nb_samples`。例如从 48000Hz 转到 44100Hz，不能仍假定每个输出 Frame 固定有 1024 个采样。

### 4.4 入队究竟复制了什么

`AVPacketPtr/AVFramePtr` 是 `shared_ptr` 别名。正确释放还依赖构造时配置的 `av_packet_free/av_frame_free` 删除器，别名本身不会自动选择 FFmpeg 的释放函数。

在这条路径中：

- 读包线程每轮新建 Packet；队列入队复制 shared_ptr，不复制一份编码负载。局部指针换成下一个 Packet 后，队列仍持有前一个。
- `avcodec_send_packet()` 成功返回后，解码器会自行保留后续所需的数据引用，必要时复制；调用方可释放自己的 Packet 引用，无需等对应 Frame 输出。若返回 EAGAIN，输入还未接受，应保留 Packet 以便重试。参见 [avcodec_send_packet](https://ffmpeg.org/doxygen/8.0/group__lavc__decoding.html)。
- 解码线程各自复用接收 Frame；`VideoConverter/AudioResampler` 每次另建带独立缓冲区的输出 Frame。
- Frame 队列持有转换结果，不是直接持有那个反复 receive 的临时 Frame，因此后续解码不会覆盖已入队的数据。
- pop 删除队列节点并把 shared_ptr 交给调用者；只有最后一个持有者释放引用时，才执行相应删除器。FFmpeg 数据缓冲区还有自己的引用计数，结构体寿命与底层缓冲区引用要分开看。

这里既有指针交接，也有实际数据转换和复制，不应把整个播放链路称为“零拷贝”。

`av_packet_unref/av_frame_unref` 释放对象当前持有的数据引用并重置字段，结构体仍可复用；`av_packet_free/av_frame_free` 还会释放结构体本身。`shared_ptr` 尚在不代表被手动 unref 的对象仍保存原来的媒体数据。

shared_ptr 的共享持有只管理寿命，不会给 Packet、Frame 的字段或数据加锁。多个指针若指向同一个 Frame，主动 unref 会改变它们共同看到的对象，不能在另一个线程仍读取时这样处理。

## 5. 视频输出：从 Frame 到屏幕

### 5.1 queued 信号完成线程交接

```text
videoPlay 工作线程
  → 从 AVContext::video_queue_ 取 AVFramePtr
  → sig_repaint(frame)
  → Qt::QueuedConnection，事件持有该 shared_ptr

GUI 线程
  → OpenGLRender::Repaint(frame)
  → repaintTexYUV420P：准备并上传纹理
  → update() 请求重绘
  → 后续 paintGL：绑定资源，绘制两个三角形
```

`Init()` 明确使用 queued connection，`AVPlayer.cpp` 也声明了 `AVFramePtr` 元类型。信号参数复制的是 shared_ptr；事件尚未处理时，它仍保持 Frame 存活。不要把这次传参理解为深拷贝整张图像。

`videoPlay` 出队、GUI 收到槽调用、纹理上传、实际绘制是几个不同时间点。`update()` 可能合并重绘请求，因此每次出队不一定对应一次独立的屏幕刷新。

当前使用普通 CPU 指针上传纹理。成功上传后，纹理保存自己的像素数据；后续 `paintGL` 采样纹理，不需要继续借用原 Frame。Frame 要保持到上传所需数据被读取完，不能在事件尚未处理时主动 unref 它。

### 5.2 YUV420P 怎样放入三张纹理

当前按偶数宽高的 YUV420P 处理：

| 纹理 | 有效尺寸 | CPU 数据 | 上传格式 |
| --- | --- | --- | --- |
| Y | W × H | `data[0] / linesize[0]` | `R8_UNorm`，`Red/UInt8` |
| U | W/2 × H/2 | `data[1] / linesize[1]` | 同上 |
| V | W/2 × H/2 | `data[2] / linesize[2]` | 同上 |

texel 是纹理中的一个数据点。`R8_UNorm` 表示每个点只存一个无符号 8 位 R 分量，采样时把 0～255 映射到 0～1；`Red/UInt8` 表示上传接口从 CPU 按单通道、无符号 8 位格式读取。这里的 R 是存储通道名，三张纹理实际分别保存 Y、U、V，不代表它们都是红色图像。格式定义见 [QOpenGLTexture](https://doc.qt.io/qt-6/qopengltexture.html)。

纹理单元 0、1、2 分别绑定这三张纹理，shader 的 `tex_y/tex_u/tex_v` 对应这些编号。采样结果的 `.r` 取出各自保存的分量，再交给后面的 YUV→RGB 计算。

`linesize` 是 CPU 每行跨度，可能包含填充；纹理宽度是有效像素数。举一个用于计算的例子：

```text
图像 640×360
Y：有效宽 640，linesize=672，高 360
U/V：有效宽 320，linesize=352，高 180

上传时每行读取有效宽度，再按对应跨度找到下一行。
不能把 Y 的下一行起点写成 data[0] + 640。
```

`QOpenGLPixelTransferOptions::setRowLength` 的单位是**像素**，`linesize` 的单位是**字节**。这里只因每个 texel 恰好一字节，数值才可直接对应；换成 RGBA 等格式时不能照搬。默认 unpack alignment 为 4，也应与实际行布局一致。参见 [Pixel Transfer Options](https://doc.qt.io/qt-6/qopenglpixeltransferoptions.html)。

### 5.3 顶点、着色器与显示区域怎样配合

`initializeGL()` 创建 shader program、VAO、VBO、EBO，通过 `glVertexAttribPointer` 将顶点步长设为五个 float：前三个是位置，后两个是纹理坐标。

当前顶点的 X/Y 位置在 -1～1 之间，经 viewport 映射到有效画面区域；纹理坐标 0～1 覆盖整张纹理。顶点位置决定画在哪里，纹理坐标决定读取图像哪里。

`vertex.vsh` 将顶点的 Y 方向取反，传递纹理坐标。`fragment.fsh` 按同一个纹理坐标分别采样 Y/U/V，给 U/V 减 0.5，使色度分量的中心回到零附近，再通过固定矩阵算 RGB。矩阵未按 Frame 的 `color_range/colorspace` 调整，因此不能认为对所有 YUV420P 来源都已正确处理颜色范围和色彩空间。

`resizeGL()` 按视频与控件比例计算 `m_zoomSize/m_pos/m_rect`。`paintGL()` 清黑背景，设置居中的 viewport，再绑定纹理、shader 与 VAO，调用 `glDrawElements` 绘制矩形，于是剩余区域形成黑边。

阶段五的鼠标坐标换算复用了 `m_rect`。阅读时只需把“有效画面区域”和“整个控件”区分开；高 DPI 下 Qt 逻辑坐标与 framebuffer 像素还需核对，不能直接当成同一单位。

### 5.4 GUI 线程并不自动具备 current context

这是当前实现必须读清的边界：

1. Qt 在调用 `initializeGL/resizeGL/paintGL` 前保证所需 context current。
2. `Repaint` 是普通 queued 槽，只保证在接收对象所属线程执行。
3. 它直接创建、销毁和上传纹理，却没有显式 `makeCurrent()`，不能仅因已进入 GUI 就认定这些 OpenGL 操作合法。
4. `initTexYUV420P` 中直接调用 `resizeGL` 也只是普通 C++ 调用，不会自动获得 Qt 调用该回调时的保证。

另外，两份 shader 声明 `#version 330 core`，片段 shader 却使用 `texture2D/gl_FragColor` 等旧接口。主程序没有显式申请所需 context format，shader 编译、链接结果也未检查。遇到黑屏应先核对实际 context、编译/链接结果与日志，不能把“函数调用过”当作渲染成功。

## 6. 音频输出：从 Frame 到扬声器

### 6.1 PCM 格式先与设备约定一致

```text
AAC_Decoder 解码得到原始音频 Frame
  → AudioResampler
  → 44100Hz / 双声道 / S16 packed Frame
  → AVContext::audio_queue_
  → audioPlay 工作线程
  → AudioRender::Write
  → QByteArray 复制 PCM
  → QIODevice::write
  → Qt 音频输出缓冲
  → 输出设备按采样率播放
```

S16 packed 表示每个样本 16 位有符号整数，声道采样交错，当前整块 PCM 可从 `data[0]` 读取。若仍是 planar 数据，只读取第一平面就不等于完整双声道 PCM。

`InitAudio(2, 44100, 16)` 与重采样目标一致。Qt 6 设置 `Int16` 并创建 `QAudioSink`；Qt 5 设置 PCM、SignedInt、16 位、小端并创建旧版 `QAudioOutput`。

格式一致还不等于设备支持。当前未检查格式支持、`start()` 返回指针和输出状态/错误，仍设置初始化标志并返回 true。真正判断声音输出要检查这些结果；API 见 [QAudioSink](https://doc.qt.io/qt-6/qaudiosink.html)，Qt 5 按项目 Kit 对照对应版本文档。

### 6.2 一块 PCM 有多少字节，能播放多久

`nb_samples` 表示每个声道的有效采样数。对当前 packed 格式：

```text
字节数 = nb_samples × 声道数 × 每样本字节数
时长（秒）= nb_samples / sample_rate

假设某次输出 Frame：
nb_samples=1024，双声道，S16，44100Hz

字节数 = 1024 × 2 × 2 = 4096 字节
时长 ≈ 1024 / 44100 = 23.22 毫秒
```

这是一个计算示例，重采样输出的 `nb_samples` 不保证始终为 1024。实际写入应使用当前 Frame 的有效采样数，而不是输入 AAC 包大小或分配容量。

`setBufferSize(409600)` 是请求的缓冲容量，实际容量要查询；它不表示当前积压了这么多数据，也不代表固定的播放延迟。

### 6.3 “有空闲”与“已写完”是两个判断

`audioPlay()` 的当前条件为：

```cpp
if (!AvailableBytes() || avContext_->audio_queue_.empty())
```

Qt 6 分支返回 `bytesFree()`；Qt 5 返回 `bytesFree()-periodSize()`；没有输出对象时返回 -1。空间判断把 0 视为不可写，却让负值通过，也未比较整块 PCM 需要的字节数；队列为空时则由另一个条件进入等待。

`Write()` 创建 `QByteArray(ptr, len)`，复制当前 PCM，再调用 `device_->write(...)`，但忽略返回值，随后 `av_frame_unref(frame.get())`。

理解返回值时用上面的 4096 字节例子：

| `write` 返回值 | 应怎样理解 |
| --- | --- |
| 4096 | 这一块已被接口全部接受，尚不表示已全部发声 |
| 2048 | 只接受前 2048 字节，剩余 2048 字节需要保留并继续写 |
| 0 | 本次没有接受数据，不能直接丢弃整块 |
| -1 | 写入失败，应处理错误 |

`QByteArray` 已复制 PCM，接口接受的数据不要求调用者继续持有原 Frame；释放 Frame 不会使这部分数据失效。当前遗漏的是未写入的尾部：返回后没有保存它，局部 QByteArray 销毁时这部分数据便被丢弃。参见 [QIODevice::write](https://doc.qt.io/qt-6/qiodevice.html#write)。

### 6.4 Qt 音频对象不会因普通调用自动换线程

音频输出对象在 GUI 初始化路径创建，`audioPlay` 却在独立 std::thread 中直接访问它和其 `QIODevice`。当前没有 queued 交接或明确的线程迁移安排，不能假设调用会自动转回 GUI，也不能把 QObject 的存在当作跨线程安全保证。

应结合对象归属、后端与具体 API 的线程约定判断。Qt 的 [Threads and QObjects](https://doc.qt.io/qt-6/threads-qobject.html)说明了普通调用、事件与对象归属的区别。阶段九再统一讨论停止与销毁的线程安排。

## 7. 队列、缓存与时间：数据取完不等于播放完

### 7.1 当前队列没有形成完整背压

`AV_Queue.h` 中 push、pop、clear 对链表修改加锁，但 `size()/empty()` 不加锁就读取普通计数，与其他线程的修改之间存在数据竞争。调用方还常先检查再 pop，并忽略 pop 返回值；检查和取出也不是一个原子操作。因此不能仅凭 push/pop 加锁就认定整个队列接口线程安全，取出是否成功应以 pop 返回值为准。

两个解码器虽有 `isFull()` 查询，视频判断 >10、音频判断 >50，读包主循环没有调用它们，`put_packet()` 也不限制入队。它们不是已生效的队列容量上限。

当前有数据就继续传递，无数据时多用 sleep 1ms 轮询；没有条件变量、统一结束标记或完整的限量策略。下游变慢时要沿实际持有者查积压：

| 位置 | 可能积压的内容 |
| --- | --- |
| 解码器 Packet 队列 | 待解码的编码数据 |
| `AVContext` Frame 队列 | 已转换的图像和 PCM |
| GUI queued 信号事件 | 已从视频 Frame 队列取走、但 GUI 还没处理的 Frame |
| Qt 音频输出缓冲 | 已接受、尚未被设备消耗完的 PCM |

视频 Frame 队列变短，可能只是数据转移到了 GUI 事件队列。真正的背压需要让下游承受能力影响上游产出，单独存在一个队列并不能做到这一点。

### 7.2 保留 PTS 不等于按 PTS 播放

当前 `videoPlay` 拿到 Frame 就发信号，没有按 PTS 等待。`audioPlay` 在队列有数据且空间判断通过时写入，设备按采样率消费。没有以音频或统一时钟调度视频，也没有基于时间差的等待、丢帧规则，因此不能说已实现音画同步。

视频转换复制了输入时间戳；音频重采样也直接沿用输入 PTS。采样率改变不会自动把这个数值换算成新的时间基。解释时间戳仍需知道它属于哪个时间基，不能仅凭输出为 44100Hz 就把任意 PTS 除以 44100。

因此，离线文件可能被快速读入队列，视频也可能快于应有节奏投递；实时流的到达节奏有时会掩盖问题，但不构成同步保证。本阶段只需能指出缺失的位置，音画同步算法不作为新增必修项目。

## 8. EOF、停止与资源寿命

### 8.1 三种“结束”不要混为一谈

| 情况 | 当前源码做什么 | 尚不能说明什么 |
| --- | --- | --- |
| `av_read_frame` 返回非零 | unref Packet，退出读包循环 | 未区分 EOF、暂时不可读与其他失败；不代表所有数据已输出 |
| Packet 或 Frame 队列为空 | 对应线程继续轮询等待 | 不代表输入结束，也不代表线程已退出 |
| 收到停止指令 | 调用 `AVPlayer::Close` | 还要核对各线程、设备和资源是否安全停止 |

对正常文件结束，每路解码线程应先消费已入队的 Packet，再提交 `nullptr` 并取完解码器的延迟输出；新增 Frame 仍要转换并交给输出，音频还需取完重采样器的延迟样本。最后还要处理输出侧剩余的 Frame 与 PCM，不能在读包 EOF 处立即结束播放。

当前没有把结束标记传到下游，也没有完成上述排空。读包线程退出后，即使已有队列逐渐被消费完，解码与输出线程仍可能一直轮询等待。

### 8.2 先读懂关闭顺序，再去阶段九检查完整性

当前主要顺序：

```text
AVPlayer::Close
  → stop_=true
  → join 音频输出线程
  → join 视频输出线程
  → reset AVDEMuxer
      → quit_=true，供 FFmpeg 中断回调检查
      → 等读包线程结束，关闭输入
      → 成员解码器析构，设置退出标志并等待解码线程
```

这是主动停止的主要调用顺序：先退出输出线程，再停止上游，不会等队列中的数据全部播放完。正常文件结束与主动停止的目标不同，不能把这条 Close 路径当作第 8.1 节的正常排空流程。

| 资源 | 本阶段应记住的寿命边界 |
| --- | --- |
| queued 视频事件的 Frame | 出队后仍由事件持有，不能只看 Frame 队列判断是否无人使用 |
| OpenGL 资源 | 纹理和缓冲区的释放也要满足 current context 条件 |
| 音频输出对象 | 停止或重启后内部 `device_` 可能失效，不应当成独立拥有对象删除 |
| `AVContext` | 持有两路 Frame 队列；输出线程退出不等于上下文和队列已经清理 |

初始化失败与重复停止的处理、退出标志的同步、回调存活及对象释放，统一放到[阶段九](项目学习规划.md#stage-9)继续检查。本阶段先读清数据与对象的寿命，不以修完关闭问题作为继续学习的条件。

## 9. 学习步骤：先跟一帧画面，再跟一块 PCM

### 第一步：对照解封装与解码示例

读 `demux_decode.c` 的核心调用，指出 Packet 的流索引在哪里分流、Frame 在哪里产生、EOF 后怎样排空。

有匹配版本的现成示例和本地音视频文件时，可直接观察解码输出及格式；否则先按代码推演，不额外新建项目。示例输出的原始格式以实际结果为准，不能预设它已经是本项目的 YUV420P 和双声道 S16。

### 第二步：沿视频两级队列跟一帧画面

沿 `FetchStream → H264_Decoder::run → VideoConverter::Convert → videoPlay → Repaint → paintGL` 阅读。

对这一帧回答：原 Packet 由谁保留？转换后的 Frame 在哪分配？queued 事件怎样延长其寿命？Y/U/V 怎样取行？哪里需要 current context？第 5.2 节的 stride 例子能解释清楚即可。

OpenGL 陌生的概念回看第 2.3 节和 Hello GL2 对应代码。有现成可运行示例时观察初始化、调整窗口与重绘。

### 第三步：沿音频两级队列跟一块 PCM

沿 `FetchStream → AAC_Decoder::run → AudioResampler::Convert → audioPlay → AudioRender::Write` 阅读。

用实际目标格式核对声道、采样率、packed/planar，再完成第 6.2、6.3 节的字节数与部分写计算。需要观察设备供数时，复用 Qt 官方音频示例。

### 第四步：核对输出、积压与正常结束

从同一条路径回答：GUI 忙时 Frame 可能留在哪？音频只写入一半时剩余数据去哪？读文件结束后哪个线程仍在等待？为什么当前 PTS 没有形成同步？

当前播放入口由信令回调传入地址，页面没有提供通用的本地文件打开功能。以上本地文件观察使用现成 FFmpeg 示例，不要求为讲义改造项目入口。真实双端拉流与正常停止复用 ENET [阶段十二统一联调](https://github.com/slimesq/ENET/blob/main/docs/项目学习规划.md#stage-12)，不在这里重复安排一轮完整联调。
