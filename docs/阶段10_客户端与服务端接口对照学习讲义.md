## 2. 先按连接区分接口

### 2.1 同一个客户端会建立多条连接

| 用途 | 客户端发起位置 | 对端与承载内容 |
| --- | --- | --- |
| 查询登录服务地址 | LoginWgt 构造及按钮回调，使用 QTcpSocket | LoadBanceSvr；发送 Login_Info，接收 LoginReply |
| 用户登录 | HandleLoadLogin 断开负载后，用同一个 QTcpSocket 对象重新连接 | LoginSvr；发送 UserLogin，接收 LoginResult |
| 本机信令登记 | RemoteWgt::handleLogined → RemoteManager::Init | SigSvr；CONTROLLED 连接，以本机码 JOIN，接收建流或输入 |
| 主动控制目标 | RemoteManager::StartRemote → PullerWgt::Connect → AVPlayer::Connect | SigSvr；另建 CONTROLLING 连接，JOIN 后请求目标并发送输入 |
| 媒体发布 | RtmpPushManager::Open → RtmpPublisher::OpenUrl | RtmpSvr；项目自定义 RTMP 客户端完成发布与媒体发送 |
| 媒体拉取 | AVPlayer::HandleStartStream → AVDEMuxer::Open | RtmpSvr；FFmpeg 另行打开 RTMP 输入，不经过客户端发布连接类 |

同一个 QTcpSocket 对象重新连接登录服务，不代表仍在使用原来的负载 TCP 连接。主动控制时，本机原有登记连接也没有因此变成控制目标的那条连接。

另有一条**服务之间**的资源上报连接：LoginSvr 的 [TcpClient](https://github.com/slimesq/ENET/blob/main/LoginServer/TcpClient.cpp) 向负载服务发送 `Monitor_body`，用于提供登录服务地址和资源信息；它不是 GUI 客户端的登录连接。

### 2.2 自定义命令与 RTMP 命令是两套协议

负载、登录和信令直接发送项目结构体。共同包头为 `len:uint16_t + cmd:uint16_t`，共 4 字节；len 包含包头。两端使用 pack(1)，没有统一逐字段转换为网络大端。

RTMP 使用握手、Message/Chunk 与 AMF 命令，不使用这个 packet_head。以下名称相似，不能互相替代：

| 名称 | 所属接口 | 作用 |
| --- | --- | --- |
| `CREATESTREAM = 7` | 自定义信令 | 通知被控端启动发布，并返回媒体 URL |
| AMF `createStream` | RTMP 媒体连接 | 取得该连接上的 Message Stream ID |
| `PLAYSTREAM = 8` | 自定义信令 | 将媒体 URL 通知控制端 |
| AMF `play` | RTMP 播放连接 | 申请播放相应媒体流 |
| `DELETESTREAM = 9` | 自定义信令 | 关联数量与停止通知 |
| RTMP Message Type `9` | 媒体连接 | 视频消息，与信令 DELETESTREAM 无关 |

下面的结构大小沿用前面阶段已核对的客户端布局；带 ResultCode/int 的尺寸以当前 4 字节布局为前提。pack(1) 不固定所有枚举宽度，也不保证任意工具链间自动兼容；换目标 ABI 时再核对，不在本阶段重做探针。

## 3. 登录：两次 Login 响应返回不同地址

### 3.1 消息、字段与处理函数

下表字段均不含共同包头；总长包含包头。在正常登录路径中，四种消息的 `cmd` 都是 `Login = 2`。负载超时等失败分支可将 LoginReply 的 cmd 改为 `ERROR = 1`（客户端名为 ERROR_），此时走 HandleError，不进入地址切换；登录服务的业务失败仍通过 LoginResult.resultCode 表达。

| 消息与方向 | 字段；当前总长 | 客户端入口 | ENET 对应入口 |
| --- | --- | --- | --- |
| Login_Info：客户端 → 负载 | timestamp:uint64_t；12 字节 | 构造函数或按钮回调发送 | LoadBanceConnection::HandleMessage → HnadleLogin |
| LoginReply：负载 → 客户端 | port:uint16_t、ip[16]；22 字节 | HandleLogin 的 is_login_==false 分支 → HandleLoadLogin | HnadleLogin 从 GetMonitorInfo 取得登录地址后回复 |
| UserLogin：客户端 → 登录 | code[20]、count[12]、passwd[33]、timestamp:uint64_t；77 字节 | HandleLoadLogin 读取输入框并发送 | LoginConnection::HandleMessage → HandleLogin |
| LoginResult：登录 → 客户端 | resultCode、port:uint16_t、ctrSvrIp[16]；26 字节 | is_login_==true 分支检查成功码，发 sig_logined | HandleLogin 查询用户与在线状态，成功时返回信令地址 |

`LoginReply.port` 在偏移 4、ip 在偏移 6；`LoginResult.resultCode` 在偏移 4、port 在偏移 8、IP 在偏移 10。不能只看到 cmd=2 就按同一结构读取。

客户端靠 is_login_ 区分这两类响应；它在连接登录服务后就置 true，不表示服务器已经验证登录成功。成功通知经 `MainWgt` 的连接进入 `RemoteWgt::handleLogined`，再初始化本机信令。

### 3.2 哪些字段确实被使用

| 字段 | 当前生产与消费 |
| --- | --- |
| timestamp | 客户端 GetTimeStamp 产生 Unix 秒；负载和登录分别校验，源码阈值为 60 秒 |
| code | LoginWgt 调用 `SetCode("345")`；服务端经 ORMManager::UserLogin 按 USER_CODE 查询 |
| count / passwd | 客户端复制账号、密码输入；当前登录处理没有用它们核对凭据 |
| LoginResult 的 IP / port | 成功时用于下一条信令连接；不携带本机识别码或认证 token |

`passwd[33]` 的 MD5 注释不代表发送路径进行了 MD5 计算。源码中的登录成功分支按 code 查询记录，并检查时间与在线状态，没有完成账号密码核对。

UserLogin 的字符数组未清零，setter 也不补字符串终止符，因此调用 SetCode("345") 后，服务端 GetCode() 不保证只读得 "345"。字符串和 TCP 分片边界沿用阶段三，不把字段声明相同视为所有输入都能安全解析。

LoginWgt 构造后会自动发起第一次查询；按钮也始终发送 Login_Info，切到登录服务后不能把它当成发送 UserLogin 的重试入口。

客户端虽定义了 Register、Destory 消息，当前没有接通它们的发送流程，HandleRegister 也为空。服务端对应的 HandleRegister、HandleDestory 分别处理注册与账号删除；Destory 会删除数据库记录，不是退出登录，因此这里没有完整的客户端注册、账号删除流程。

## 4. 把五种标识分清，再跟一个会话

### 4.1 相同默认值不等于同一个字段

| 标识 | 产生位置 | 进入的字段与用途 |
| --- | --- | --- |
| 登录码 | HandleLoadLogin 调用 `SetCode("345")` | UserLogin.code[20]，查登录数据库；字符串有效性见第 3.2 节 |
| 本机识别码 | RemoteWgt 本机输入框，默认 `"345"` | CONTROLLED 连接的 JOIN.id[10]，登记可被查找的本机连接 |
| 远程目标码 | 远程识别码输入框 | CONTROLLING 连接的 OBTAINSTREAM.id[10]，查目标连接 |
| 控制连接注册码 | SigConnection::Join 固定 `"154564"` | CONTROLLING 连接自己的 JOIN.id，不是远程目标 |
| 媒体流名 | doCtreatStream 的进程内 `++streamIndex` | URL 尾部，供 RTMP Session 定位媒体流 |

登录码与本机信令码来自独立位置，没有自动绑定；改本机输入框不会改 LoginWgt 中的固定登录码。协议也没有把 CONTROLLED/CONTROLLING 作为字段发给服务端；服务端收到 JOIN 后登记 id，随后按业务请求形成自己的角色状态。

客户端 State 与服务端 RoleState 是本地状态，不在这些包里传输。两端枚举数值不同本身不构成线上字段冲突，状态是否同步要看实际迁移。

### 4.2 一个用于对照的身份例子

设 A 主动控制 B：

```text
A 原有本机登记连接：JOIN.id = "345"
B 本机登记连接：    JOIN.id = "346"

A 新建控制连接：    JOIN.id = "154564"
随后申请目标：      OBTAINSTREAM.id = "346"
```

登录数据库使用的 code 另按两端测试用户核对，不能从上图推断它会自动改变。

服务端 ConnectionManager 用 JOIN.id 查找和登记连接。相同控制注册码会导致多个控制连接冲突；同一进程生成的流编号也不是全局唯一标识。以上例子用于跟清字段，不要求在本阶段增加多个控制端实验。

## 5. 信令：从获取目标到通知播放

### 5.1 逐条对应发送、处理与消费

| 消息 | cmd、包体 | 发送方 → 接收入口 → 后续动作 |
| --- | --- | --- |
| JOIN 请求/应答 | 5；请求 id[10]，应答 result | 客户端 Join → 服务端 HandleJion/ConnectionManager → 客户端 doJoin |
| OBTAINSTREAM 请求/应答 | 6；请求目标 id[10]，应答 result | 客户端 obtainStream → 服务端 HandleObtainStream/DoObtainStream；客户端当前无应答分支 |
| CREATESTREAM 通知/应答 | 7；通知无额外字段，应答 result+streamAddres[70] | 服务端通知被控连接 → doCtreatStream/启动回调 → 服务端 HandleCreateStream/DoCreateStream |
| PLAYSTREAM 通知 | 8；result+streamAddres[70] | 服务端 DoCreateStream 或已有流分支 → 控制端 doPlayStream → AVPlayer::HandleStartStream |
| DELETESTREAM 通知 | 9；streamCount:int | 服务端 Clear 通知关联连接 → 客户端 doDeleteStream；数量为 0 才调用停止回调 |

客户端成功值 S_OK_=0 与服务端 SUCCESSFUL=0 相同，SERVER_ERROR=1 与 ERROR=1 也相同，名称差异不改变线上值。

`PlayStreamReplay_body` 虽有定义，当前没有形成实际的播放应答往返，不能补画一个源码里没有的确认步骤。

### 5.2 目标空闲时的正常主线

```text
A 控制连接 JOIN 成功
  → doJoin → obtainStream(目标 B)
  → A 本地设 PULLER

服务端 SigConnection::DoObtainStream 找到空闲 B
  → A 的服务端连接设 PULLER，conn_ 指向 B
  → 双方 objectes_ 记录关联
  → 发 CREATESTREAM 给 B，发 OBTAINSTREAM 成功给 A

B 的 SigConnection::doCtreatStream
  → 生成 URL → RemoteManager::HandleStartStream → RtmpPushManager::Open
  → 回调返回 true，回复 CREATESTREAM(result=0, URL)
  → B 本地设 PUSHER

服务端 SigConnection::DoCreateStream
  → 保存 URL，检查关联连接状态
  → 对应控制连接为 PULLER 时，将被控端的服务端连接设为 PUSHER
  → 发 PLAYSTREAM(result=0, URL) 给 A

A 的 SigConnection::doPlayStream
  → AVPlayer::HandleStartStream → AVDEMuxer::Open
  → 异步打开媒体，启动输出线程
```

服务端 DoCreateStream 没有按回复中的 result 决定成功，主要看 URL 是否为空及关联状态；因此应同时对照“字段存在”和“处理函数有没有使用该字段”。本阶段正常链路仍以前面步骤已成功为前提。

### 5.3 只补影响接口判断的分支

| 情况 | 两端源码可以确认的结果 |
| --- | --- |
| 目标不存在 | 服务端回复 OBTAINSTREAM/ERROR，不发 CREATESTREAM；客户端没有处理该应答，仍可能保持本地 PULLER |
| 目标信令状态为 PUSHER，且已有 URL | 服务端直接发 PLAYSTREAM；该分支遗漏 conn_ 赋值，对首次申请的控制连接可能出现可取播放地址、输入却无法转发 |
| 关联连接断开 | 服务端 DisConnected → Clear，向关联方发送其移除关联后的 streamCount |
| 客户端收到数量为 0 的 DELETESTREAM | 调用停止回调；不代表本地状态和所有资源已恢复，继续对照阶段九 |

streamCount 来自**信令关联表**，不是向 RtmpSvr 查询的实际观看人数。当前客户端未见构造并发送信令 DELETESTREAM 的路径；窗口关闭也未接通可靠的主动停止流程，不能仅凭服务端支持该命令就认定两端已有完整往返。

## 6. 媒体：按 URL 和真实消息类型对应

### 6.1 谁产生 URL，谁查找 Session

被控端 `doCtreatStream` 当前生成：

`rtmp://192.168.31.30:1935/live/<递增编号>`

该地址由客户端产生；SigSvr 保存并转交，不负责解析 RTMP 或验证发布是否可用。控制端将同一个 URL 交给 FFmpeg。

| URL 部分 | 客户端发布侧 | ENET 媒体侧 |
| --- | --- | --- |
| host、port | ParseRtmpUrl 后建立媒体 TCP | RtmpSvr 的监听地址 |
| app，例如 live | Connect 的 AMF 对象字段 | HandleConnect 取得 app |
| stream name，例如编号 2 | Publish 的命令参数 | HandleInvoke 读取流名并组成路径，再进入 HandlePublish/HandlePlay |
| /live/2 | 发布与播放应指向同一路径 | 按 `/app/stream_name` 查找 RtmpSession |

发布与播放是两条媒体连接，服务端分别创建 RtmpConnection。先核对它们连接的是同一个 RtmpSvr 实例，再按 `/app/stream_name` 对应 Session；不同媒体服务实例上的同名路径不代表同一 Session。

各连接上的 Message Stream ID 不必相同，也不能用信令识别码或 Chunk ID 代替媒体流路径。

### 6.2 命令与媒体消息入口

| 动作 | 客户端入口 | ENET 对应入口与应答 |
| --- | --- | --- |
| AMF connect | RtmpConnection::Connect，带 app | HandleInvoke → HandleConnect；回复 _result/NetConnection.Connect.Success |
| AMF createStream | CretaeStream | HandleCreateStream；回复 _result 和该连接的流 ID |
| AMF publish | Publish，带 stream name | HandlePublish；回复 onStatus/NetStream.Publish.Start 或错误 |
| AMF play | 项目入口为 AVDEMuxer::FetchStreamInfo，协议由 FFmpeg 处理 | HandlePlay；回复 NetStream.Play.Reset/NetStream.Play.Start，加入 Session |
| 视频 Message Type 9 | SendVideoData | HandleVideo → RtmpSession::SendMediaData → 各播放连接 SendMediaData |
| 音频 Message Type 8 | SendAudioData | HandleAudio → RtmpSession::SendMediaData → 各播放连接 SendMediaData |

发布侧的应答回到客户端 `RtmpConnection::HandleMessage → HandleInvoke`。其中 `_result` 进入 HandleResult：连接命令成功后调用 CretaeStream，创建流成功后保存 stream_id_ 并调用 Publish；`onStatus` 进入 HandleOnStatus，识别 NetStream.Publish.Start 并设置 is_publishing_。

播放应答由 FFmpeg 内部处理，不进入这份客户端发布连接类。项目通过 `av_read_frame` 取得解封装后的 Packet，再按 stream_index 送入视频或音频解码队列，接到阶段八的 Frame 队列与输出路径。

服务端负责媒体分发和配置缓存，H.264/AAC 解码与画面声音输出由客户端完成。这条媒体路径使用独立的 RTMP 连接，不经过 SigSvr 的键鼠转发关系。

### 6.3 AAC 配置：沿真实发送入口判断差异

当前 RtmpPublisher 首关键包分支把 AVC 配置和 AAC 配置都交给 SendVideoData。对应关系为：

```text
AAC 配置负载 AF 00 ...
  → 客户端 SendVideoData
  → 外层 RTMP Message Type = 9
  → ENET HandleVideo
  → 不进入 HandleAudio 的 AAC 配置识别与缓存分支

普通 AAC 负载 AF 01 ...
  → SendAudioData → Type 8 → HandleAudio
```

内部负载看起来像 AAC，不会自动纠正外层 type。服务端正常 AAC 配置缓存要求先进入 HandleAudio，再检查 SoundFormat 与第二字节。

ENET 使用的 0x18/0x19 是**内部序列头分类标记**，重新发送时仍映射为线上的视频 type 9、音频 type 8；不要把内部标记当成线上独立的 RTMP 消息类型。封装细节复用阶段七和 ENET 阶段九，此处不重做编码实验。

### 6.4 成功确认分属不同层次

| 动作或返回结果 | 可以确认到哪一步 | 还没有确认什么 |
| --- | --- | --- |
| CREATESTREAM 回复成功和 URL | 启动回调返回 true；若实际执行的是已绑定的 RtmpPushManager::Open，可追到打开发布 TCP、提交握手并创建采编线程 | 发布获准、配置有效、控制端首帧 |
| 收到 NetStream.Publish.Start | RTMP 服务端接受了发布 | 当前发送逻辑未以该状态作为门槛，也不证明播放成功 |
| 收到 NetStream.Play.Start | 服务端处理了播放请求 | 当前 HandlePlay 可创建尚无发布者的空 Session，不能据此证明有媒体 |
| AVDEMuxer::Open 返回 true | 已发起读包线程 | 实际打开、流信息、解码和 GUI/音频输出成功 |

对同一会话，应把 URL、发布应答、服务端媒体分发与最终画面声音对应起来；不能只凭一条“成功”日志跳过后续层次。

## 7. 输入：生产、透明转发与最终执行

### 7.1 四类输入共用同一条控制信令连接

```text
控制端 AVPlayer 的 Qt 事件函数
  → 用客户端结构体构造消息并 Send
  → 服务端 SigConnection::HandleOtherMessage
      → 要求服务端连接 state_==PULLER 且 conn_ 有目标
      → 按 data->len 原样转发
  → 被控端 SigConnection 解码
  → SendInput 或 QCursor::setPos
```

输入包不含目标识别码，服务端靠前面建立的 conn_ 转发。它读取头部选择分支，但没有按服务端的键鼠结构体解码包体。

| 消息与 cmd | 客户端包体 | 生产入口 → 被控端消费入口 |
| --- | --- | --- |
| MOUSE，10 | type:MouseKeyType、mouseButtons:MouseType，各 1 字节 | mousePressEvent/mouseReleaseEvent → doMouseEvent |
| MOUSEMOVE，11 | xl_ratio/xr_ratio/yl_ratio/yr_ratio，各 uint8_t | mouseMoveEvent/GetPosRation → doMouseMoveEvent |
| KEY，12 | type:MouseKeyType（1 字节）、key:uint16_t | keyPressEvent/keyReleaseEvent → doKeyEvent |
| WHEEL，13 | wheel:int8_t | wheelEvent → doWheelEvent |

移动发送的是画面区域内的比例拆分，接收方还原比例后计算本机坐标；按下/松开值为 0/1；滚轮方向为 ±1，接收端乘 240。坐标、键值与 Windows API 的细节复用阶段五。

### 7.2 声明不同，先看哪里真正读取它

| 声明差异 | 当前实际影响 |
| --- | --- |
| 客户端 KEY 为 type→key，服务端为 key→type | 定义不一致，但服务端原样转发不会重排字节；两端客户端使用同一定义时，不能据此断言实际键盘必然错位 |
| 客户端 WHEEL 为 int8_t，服务端为 uint8_t | 当前转发不改变 0xFF；只有按服务端字段解码时，才会出现 −1 与 255 的解释差异 |
| mouseButtons/mouseType、RELEASE/RELESE 名称不同 | 字段名与拼写不进入线上数据，需核对的是布局与数值 |

需要与这些声明差异分开的是客户端实际代码问题：`keyReleaseEvent` 没有给 body.type 赋值，Qt 键值也没有完整映射为 Windows VK。它们会直接进入最终消费路径，不能归因于服务端透明转发时“自动按另一种结构转换”。

分片、长度检查和解析无进展的边界继续复用阶段三、五及 ENET 阶段二；对照表不代表所有消息解析已经正确。

## 9. 学习步骤：对照登录、建流与输入

### 第一步：沿登录与连接表核对地址

从 Login_Info、LoginReply、UserLogin、LoginResult 找到双方入口，指出两种响应的布局和地址含义。再用第 4 节例子区分本机登记连接和主动控制连接。

### 第二步：跟一轮建流交互及同一 URL

沿 OBTAINSTREAM → CREATESTREAM → PLAYSTREAM 找发送、处理和消费入口，确认 URL 在哪产生、服务端是否检查 result。再将同一 URL 对到 RTMP 的 publish/play 与 Session，分清建流回复、发布应答和首帧。

### 第三步：跟一条输入消息，核对配置

任选 KEY 或 MOUSEMOVE，从 AVPlayer 跟到服务端 HandleOtherMessage，再到被控端消费函数，指出服务端实际读取的字段和原样转发的字节。再用第 7.2 节的 KEY 例子，区分两端声明差异与客户端实际的赋值、键值处理问题。

最后按第 8 节核对本次配置。已有布局、媒体和停止观察直接复用；不要求先修完所有接口问题，也不重复搭服务或再运行一轮完整会话。
